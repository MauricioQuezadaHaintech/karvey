Plugin for Claude Code · Development method

Karvey

Karvey is a word of the Ona language of the Selknam people of Patagonia, meaning Afán — zeal, the drive to get things done.

  • v3.13.0
  • Apache-2.0
  • SDD · spec-driven
  • stack-agnostic
  • spiral

Karvey is a spec-driven development (SDD) method for Claude Code. It takes a change from idea to production through a 13-phase pipeline (0–12) with approval gates, plus a support layer of skills you can invoke at any time. It is stack-agnostic (web, iOS/Android, desktop, CLI, API, embedded) and works as a spiral, not a line: whatever turns up in testing, QA or the real runtime goes back to where it belongs, so nothing gets dropped.

This page complements the repo README: it explains how the method thinks and draws the complete map of the plugin.

02 · Principles

How it thinks

Seven ideas hold the whole method up. Every skill and every rule is the concrete form of one of them.

  1. Spec-drivenEvery change starts from a PRD (prd.md); EARS requirements trace back to it and the living specs accumulate, per capability, what the system does.
  2. Stack-agnosticThe project declares its targets and each phase adapts: a CLI’s mockup is a transcript of commands; an API’s, request/response examples.
  3. Approval gatesEach phase produces a document in docs/spec/ and asks for your OK before moving on. --autoplan batches the planning gates; it does not skip them.
  4. Spiral, not lineThe pipeline is the happy path. Findings come back along three edges (bug, spec-gap, emergent) and a change is only ready when it converges.
  5. Nothing left hangingA mandatory closing ritual for every phase and task, a discovery backlog, a BUG-NN tracker and cleanup of absorbed branches: nothing gets dropped.
  6. Human OK for productionMerging to the production branch requires explicit approval, recorded in approvals.prod. It is never delegated to an agent and there is never a manual deploy.
  7. Measured, not rememberedOnly what was verified in the session is reported, with command and evidence. The handoff is captured with commands and the session hook checks the saved state against the live repos.

12

Archive

/karvey:karvey-archive <change-id>
What it does
Merges the spec-deltas into the living specs, archives the change and closes the Epic. Sweeps the backlog (offers to promote emergent items to new change-ids) and the branches. Recommended: karvey-retro + karvey-docs.
Produces
An updated specs/{capability}/spec.md, changes/archive/{fecha}-{change-id}/.
Rules
living-specsbacklogphase-closedeploy-workflow

Gate: completeness check; the change does not close while one of its branches is still alive.

Change types: feature, ops, hotfix and parent change
  • ops (IAM, DNS, secrets, console): init → requirements (lite) → infra (command plan) → tasks ([human]/[Infra]) → execution + verification → archive. Mockup, design and architecture are skipped (the latter only unless trust boundaries change).
  • hotfix: iterate (BUG-NN) → impl → test (regression) → deploy, with fix + BUG-NN + regression test in the same PR. Requirements are reopened only if the defect is a spec-gap.
  • Parent change (links.children): has no code of its own; shows the phase of each child ({change-id}@{repo}) and moves to deployed only when every child is deployed or discarded by decision.
  • Documentation-only PR: lightweight CI (spec lint) instead of build/test/deploy; it never triggers a deployment.

05 · The spiral

The iteration loop

Afán — zeal: you do not stop until the result is truly achieved. test, qa and browse only observe and classify (they log to findings.md); karvey-iterate is the only one that routes.

06 · At any time

Support layer · 18 support skills

They are not phases: they do not push spec.json:phase forward. The one exception is karvey-iterate, which may make the controlled backward transition of the revision sub-cycle. They honour the same gates and hooks.

karvey-iterate

iteration

The iteration engine: reads findings.md, confirms the type and routes each finding to bug, spec-gap or emergent. The only place where the loop’s logic lives.

When: findings turned up, or the spec proved wrong or incomplete.

karvey-investigate

diagnosis

Root-cause debugging. Iron Law: no fix without investigating. Dates the symptom, asks what changed before asking what is wrong, follows the data across repos and separates the cause from latent fragility.

When: something fails and nobody understands why.

karvey-second-opinion

review

Adversarial review with another model (Claude vs GPT/Codex/Gemini). Review (PASS/FAIL), Challenge and Consult modes. It complements QA’s security gate; it never approves on its own.

When: before releasing something sensitive.

karvey-health

quality

A 0–10 quality score (type-check, lint, tests, dead code) with a trend, plus method readiness: skills installed and pinned inputs (repo path @commit) still current.

When: periodic check-ups or multi-repo work.

karvey-devex

review

Reviews the developer experience: walks the real onboarding, measures time-to-hello-world and finds friction and “docs that lie”. Plan and live modes.

When: auditing onboarding or DX.

karvey-retro

review

Cycle retrospective: velocity, test health, per-person breakdown, streaks and improvement opportunities from the commit history.

When: closing a cycle (recommended at archive).

karvey-browse

eyes

Gives the agent eyes in the real runtime: browser (web), simulator or device (mobile), terminal (CLI). Click, screenshot, inspect; imports cookies for authenticated views.

When: to see what the user sees; it also writes to findings.md.

karvey-checkpoint

state / handoff

save / restore of the change’s checkpoint and the agent’s handoff: identity, manifest, board, checklist, measured repo state (state.json), standing decisions and scheduled tasks.

When: rotating a session or handing work over, with one agent or several.

karvey-docs

documentation

Documentation engineer: generates Diátaxis docs (tutorial, how-to, reference, explanation) from the code, updates stale docs and exports Markdown to PDF.

When: after a release (recommended at archive).

karvey-diagram

diagrams

Natural language to diagram: mermaid source + editable .excalidraw + rendered SVG/PNG. Works offline.

When: flow, sequence, architecture or ER.

karvey-guard

guardrails

Installs or removes the enforcement hooks, grants a temporary plan-gate override, applies an edit-lock to a directory (--freeze) and runs the verification checklist (--verify, read-only).

When: sensitive work, or to enforce the flow.

karvey-team

team · optional

Opt-in team layer: init, census, relay, cost. Roles, manifests, boards, census, relay and spend measurement.

When: only after reading rules/team.md; Karvey is complete with a single agent.

karvey-decisions

team · decisions

A single numbered log (D-NN business, C-NN direction) that changes cite. cross checks a question against the log before declaring anything blocked.

When: making, looking up or citing a decision.

karvey-standards

standards

Extracts the team’s golden paths (db, backend, frontend…) from the real system into the team’s standards repo. Re-runnable; --refresh promotes recurring deviations. It never writes to the public plugin.

When: bootstrapping or refreshing the standards.

karvey-import

import

Converts Kiro specs (.kiro/specs/*) or gstack specs into the docs/spec/ structure. Non-destructive towards the source; gates come in unapproved so they are revalidated.

When: migrating from Kiro or gstack.

karvey-benchmark-models

benchmark

Compares models side by side on a skill or task: latency, tokens, cost and LLM-judged quality (optional).

When: deciding which model to use.

karvey-scrape

scrape

Extracts data from a website: the first time it prototypes the extraction, then encodes it as a reusable, tested script or skill.

When: extracting web data repeatably.

karvey-context

context · read-only

Dashboard: project config, capabilities, active and archived changes, sprint, deploy queue / landing report (what is in dev, in prod, ready to release), backlog and live branches.

When: at any time; it never writes.

08 · What runs on its own and what you choose

Hooks

A skill is guidance: the model follows it voluntarily and it guarantees nothing. A hook actually blocks. Karvey separates what comes active with the plugin from what each project decides to enable.

Active on install

automatic SessionStart · karvey-session-context.sh (on startup|resume|compact|clear, 10 s timeout).

  • Re-injects identity, manifest, board, checklist and handoff (looks for docs/spec/team.json, a legacy .ceo-agentes or docs/spec/agent/).
  • Measures: for each repo in state.json it compares branch, last commit and uncommitted changes against the live tree → matches or DRIFT — branch X -> Y.
  • Says to run /karvey-checkpoint restore first if there is an active change, drift, or no handoff.
  • 3.10 In a Karvey project without team settings it prints one line pointing to /karvey:karvey-init --settings.
  • Outside a Karvey project it is inert: prints nothing and exits 0. The plugin’s hooks add to yours; they do not replace them.

by hand, once Statusline · karvey-statusline.sh: context, account limits with the time of the next reset and the time remaining for each window (e.g. 5h 29% ↻18:05 (1h31m) · 7d 35% ↻jue 21:20 (2d4h), clock per KARVEY_TZ, the system time zone by default), hours, cost and a “TIME TO ROTATE” warning. A plugin cannot declare a statusline, so you paste it into your ~/.claude/settings.json. It runs outside the turn (costs no tokens) and needs bash + python3.

{
  "statusLine": {
    "type": "command",
    "command": "bash ~/.claude/plugins/<marketplace>/karvey/<version>/hooks/karvey-statusline.sh",
    "padding": 0
  }
}

Thresholds: KARVEY_ROTATE_CTX_YELLOW (100000), KARVEY_ROTATE_CTX_RED (150000), KARVEY_ROTATE_HOURS (8). The 150k comes from measurement: at 588k of context a turn costs 7× what it costs at 80k.

10 · Delivery

Deploy and branches

Deployment is triggered by the pipeline, never by hand by a person or an agent: a push to dev deploys dev; a merge to master deploys prod. The names come from project.json:branch_flow.

  1. feature/{change-id}Development and one commit per task. Never commit on dev or master.
  2. devpull → merge → push ⇒ DEV pipeline → canary.
  3. PR dev → masterpull first; the PR’s gates (CI + branch policies) green.
  4. masterMerge only with a human OK ⇒ PROD pipeline → canary.
  5. HygieneAbsorbed branches deleted (remote + local); unabsorbed ones are reported.

6-step checklist

  1. Am I on a feature branch?
  2. Did I update CHANGELOG.md?
  3. Did I commit everything pending?
  4. Did I push the branch?
  5. Did I merge to dev?
  6. Did I push dev?

Only then does the pipeline deploy dev. For prod the verification is repeated, and the PR goes through with approval.

PR gates and human OK

CI and branch policies (build validation, required reviewers, status checks) run on the merge commit and see what the local check does not. Approval is never requested on a red gate: that turns approval into a rubber stamp. Skipping a policy is the human’s decision and responsibility.

The OK is recorded in git: approvals.prod = { by, date, ref: D-NN }. The production gate is never delegated to an agent.

Post-deploy canary

After every deploy (dev and prod), several spaced-out iterations against the real runtime: console, performance, pages/endpoints, with evidence. In dev a regression stops promotion to prod; in prod it raises an alert and recommends a rollback, also via pipeline. It reinforces zero downtime.

Branch hygiene

Absorption is verified: git branch -r --merged, git cherry and the tree test with git merge-tree --write-tree (squash). Absorbed → deleted (git branch -d, never -D). Not absorbed → never deleted: it is reported with its commits and the human decides. Counts are reported; nothing is ever cleaned up silently.

Version bump and visible version

Every deploy bumps the version (semver major.minor.rev, never reused) and adds the CHANGELOG.md entry, per component and per repo. A front shows it by environment: DEV shows the dev version v3.10.1-dev.42+74571ae with a DEV mark; PROD shows the release version v3.10.1.

The version is read from the version file (package.json, pyproject.toml…) at build time — never from a pipeline variable, which goes stale silently. The pipeline only provides environment, build number and commit. The canary checks that the visible version matches the environment.

Multi-repo: the flow applies in each repo following the dependency order in architecture.md (e.g. DB → backend → frontend). Semver + CHANGELOG before the push; version visible in the frontend (recommended).

11 · Optional

Agent-team layer

The pipeline carries the axis of the work; this layer adds the axis of the worker: who carries it, what role they have, how they survive a context reset and how several coordinate without stepping on each other. It is opt-in and not the recommended default. Without docs/spec/team.json, the layer does not exist for the project.

An honest cost warning (measured, not theoretical). The run that gave rise to the rule: a team of 6 agents on a real product, 3 days, ≈ US$1,000, and it ended up going back to a single agent with good instructions. A turn at 588k of context cost 7× one at 80k; 31% of the turns accounted for 48% of the spend. Every hop between agents is fresh context for the receiver: there is no shared cache across sessions, and the same background is re-read and paid for on each side.

Don’t use a team when…

  • the budget matters;
  • the work fits in one context;
  • the split would be by topic rather than by repo with a real owner;
  • nobody is measuring the spend.

It earns its cost with…

  • truly parallel work in separate repos;
  • long, independent workstreams;
  • roles that need other tools or permissions (a machine with a browser, a console operated by a person).

If it is on, measure it

karvey-team cost writes the report into the repo. Also: init (shows the cost table and confirms before writing), census (an inventory, not an address book) and relay (sessions ready to rotate). Rotation by threshold: 150k of context or 24 h by default.

The handoff and the session hook work the same with a single agent (docs/spec/agent/); with a team only its location changes ({ops_repo}/agents/<rol>/).

02 · Principios

Cómo se piensa

Siete ideas sostienen todo el método. Cada skill y cada regla es la forma concreta de alguna de ellas.

  1. Guiado por especificacionesTodo cambio nace de un PRD (prd.md); los requisitos EARS se trazan a él y las specs vivas acumulan por capability lo que el sistema hace.
  2. Agnóstico de stackEl proyecto declara sus targets y cada fase se adapta: el mockup de una CLI es una transcripción de comandos; el de una API, ejemplos de request/response.
  3. Compuertas de aprobaciónCada fase produce un documento en docs/spec/ y pide tu OK antes de avanzar. --autoplan agrupa las compuertas de planificación, no las salta.
  4. Espiral, no líneaEl pipeline es el camino feliz. Los hallazgos vuelven por tres aristas (bug, spec-gap, emergente) y un cambio solo está listo cuando converge.
  5. Nada queda en el aireRitual de cierre obligatorio en cada fase y tarea, backlog de descubrimiento, tracker BUG-NN y limpieza de ramas absorbidas: nada queda botado.
  6. OK humano para producciónEl merge a la rama de producción exige aprobación explícita, registrada en approvals.prod. Nunca se delega a un agente y nunca hay deploy manual.
  7. Medido, no recordadoSe reporta lo verificado en la sesión, con comando y evidencia. El handoff se captura con comandos y el hook de sesión contrasta el estado guardado contra los repos vivos.

10 · Entrega

Deploy y ramas

El despliegue lo dispara el pipeline, nunca una persona ni un agente a mano: push a dev despliega dev; merge a master despliega prod. Los nombres salen de project.json:branch_flow.

  1. feature/{change-id}Desarrollo y commit por tarea. Nunca commit en dev ni master.
  2. devpull → merge → push ⇒ pipeline DEV → canary.
  3. PR dev → masterpull antes; gates del PR (CI + políticas de rama) en verde.
  4. masterMerge solo con OK humano ⇒ pipeline PROD → canary.
  5. HigieneRamas absorbidas borradas (remota + local); las no absorbidas se reportan.

Checklist de 6 pasos

  1. ¿Estoy en una feature branch?
  2. ¿Actualicé CHANGELOG.md?
  3. ¿Commiteé todo lo pendiente?
  4. ¿Hice push de la rama?
  5. ¿Hice merge a dev?
  6. ¿Hice push de dev?

Recién ahí el pipeline despliega dev. Para prod se repite la verificación y el PR con aprobación.

Gates del PR y OK humano

CI y políticas de rama (build validation, revisores obligatorios, status checks) corren sobre el merge commit y ven lo que el chequeo local no ve. Nunca se pide aprobar sobre un gate rojo: eso vuelve la aprobación un timbre. Saltarse una política es decisión y responsabilidad del humano.

El OK queda en git: approvals.prod = { by, date, ref: D-NN }. El gate de producción nunca se delega a un agente.

Canary post-deploy

Tras cada deploy (dev y prod), varias iteraciones espaciadas sobre el runtime real: consola, rendimiento, páginas/endpoints, con evidencia. En dev una regresión detiene el paso a prod; en prod se alerta y se recomienda rollback, también por pipeline. Refuerza el cero downtime.

Higiene de ramas

La absorción se verifica: git branch -r --merged, git cherry y la prueba de árbol con git merge-tree --write-tree (squash). Absorbida → se borra (git branch -d, nunca -D). No absorbida → nunca se borra: se reporta con sus commits y el humano decide. Se informan los conteos, nunca se limpia en silencio.

Bump de versión y versión visible

Cada deploy sube la versión (semver major.minor.rev, nunca se reutiliza) y agrega la entrada en CHANGELOG.md, por componente y por repo. El front la muestra según el ambiente: DEV muestra la versión de desarrollo v3.10.1-dev.42+74571ae con una marca DEV; PROD muestra la versión de release v3.10.1.

La versión se lee del archivo de versión (package.json, pyproject.toml…) al compilar — nunca de una variable del pipeline, que queda pegada sin avisar. El pipeline solo aporta ambiente, número de build y commit. El canary verifica que la versión visible corresponda al ambiente.

Multi-repo: el flujo se aplica en cada repo respetando el orden de dependencias de architecture.md (p. ej. DB → backend → frontend). Semver + CHANGELOG antes del push; versión visible en el frontend (recomendado).

11 · Opcional

Capa de equipo de agentes

El pipeline lleva el eje del trabajo; esta capa suma el eje del trabajador: quién lo lleva, qué rol tiene, cómo sobrevive a un reinicio de contexto y cómo se coordinan varios sin pisarse. Es opt-in y no es la opción recomendada por defecto. Sin docs/spec/team.json, la capa no existe para el proyecto.

Aviso honesto de costo (medido, no teórico). La corrida que originó la regla: un equipo de 6 agentes en un producto real, 3 días, ≈ US$1.000, y terminó volviendo a un solo agente con buenas instrucciones. Un turno a 588k de contexto costó 7× que a 80k; el 31% de los turnos concentró el 48% del gasto. Cada salto entre agentes es contexto nuevo para quien recibe: no hay caché compartida entre sesiones y el mismo trasfondo se relee y se paga en cada lado.

No uses un equipo cuando…

  • el presupuesto importa;
  • el trabajo cabe en un contexto;
  • la división sería por tema y no por repo con dueño real;
  • nadie está midiendo el gasto.

Se gana su costo con…

  • trabajo realmente paralelo en repos separados;
  • líneas largas e independientes;
  • roles que necesitan otras herramientas o permisos (una máquina con navegador, una consola operada por una persona).

Si está encendida, mídela

karvey-team cost escribe el reporte en el repo. Además: init (muestra la tabla de costos y confirma antes de escribir), census (inventario, no libreta de direcciones) y relay (sesiones listas para rotar). Rotación por umbral: 150k de contexto o 24 h por defecto.

El handoff y el hook de sesión funcionan igual con un solo agente (docs/spec/agent/); con equipo solo cambia dónde vive ({ops_repo}/agents/<rol>/).

02 · Princípios

Como pensa

Sete ideias sustentam todo o método. Cada skill e cada regra é a forma concreta de uma delas.

  1. Orientado a especificaçãoToda mudança parte de um PRD (prd.md); os requisitos EARS remetem a ele e as living specs acumulam, por capacidade, o que o sistema faz.
  2. Agnóstico de stackO projeto declara seus targets e cada fase se adapta: o mockup de uma CLI é uma transcrição de comandos; o de uma API, exemplos de request/response.
  3. Gates de aprovaçãoCada fase produz um documento em docs/spec/ e pede o seu OK antes de seguir. --autoplan agrupa os gates de planejamento; não os pula.
  4. Espiral, não linhaO pipeline é o caminho feliz. Os achados voltam por três arestas (bug, spec-gap, emergente) e uma mudança só está pronta quando converge.
  5. Nada fica penduradoUm ritual de fechamento obrigatório para cada fase e tarefa, um backlog de descobertas, um tracker BUG-NN e a limpeza das branches absorvidas: nada se perde.
  6. OK humano para produçãoO merge na branch de produção exige aprovação explícita, registrada em approvals.prod. Nunca é delegado a um agente e nunca há deploy manual.
  7. Medido, não lembradoSó se reporta o que foi verificado na sessão, com comando e evidência. O handoff é capturado com comandos e o hook de sessão confere o estado salvo contra os repositórios vivos.

O que faz

Tipos de mudança: feature, ops, hotfix e mudança-mãe

  • PR só de documentação: CI leve (lint da spec) em vez de build/test/deploy; nunca dispara um deploy.

05 · A espiral

O ciclo de iteração

Afán — empenho: não se para até que o resultado seja realmente alcançado. test, qa e browse apenas observam e classificam (registram em findings.md); karvey-iterate é o único que encaminha.

Tipos de achado e sua aresta
TipoTeste decisivoArestaBloqueia?
bug“A spec está certa, o código está errado.”Tracker BUG-NN com histórico de estados (DETECTADO → DIAGNOSTICADO → EN FIX → RESUELTO → REABIERTO — detectado, diagnosticado, em correção, resolvido, reaberto) → microciclo impl→test→qa.Sim, até ser resolvido.
spec-gap“Se tivéssemos especificado direito, a implementação teria sido diferente.”Subciclo de revisão: approvals.requirements vai para false, +1 em iteration_count, uma entrada em revision_history; só o requisito afetado é emendado e reaprovado.Sim, até ser resolvido.
emergente“Boa ideia, mas é outra mudança.”docs/spec/backlog.md (fonte da verdade) + um espelho no tracker → um novo change-id na varredura do arquivamento.Não; basta registrá-lo.

06 · A qualquer momento

Camada de apoio · 18 skills de apoio

Não são fases: não avançam o spec.json:phase. A única exceção é o karvey-iterate, que pode fazer a transição controlada para trás do subciclo de revisão. Respeitam os mesmos gates e hooks.

karvey-iterate

iteração

O motor de iteração: lê o findings.md, confirma o tipo e encaminha cada achado para bug, spec-gap ou emergente. O único lugar onde vive a lógica do ciclo.

Quando: surgiram achados, ou a spec se mostrou errada ou incompleta.

karvey-investigate

diagnóstico

Depuração da causa raiz. Lei de Ferro: nenhuma correção sem investigar. Data o sintoma, pergunta o que mudou antes de perguntar o que está errado, segue os dados entre repositórios e separa a causa da fragilidade latente.

Quando: algo falha e ninguém entende por quê.

karvey-second-opinion

revisão

Revisão adversarial com outro modelo (Claude vs GPT/Codex/Gemini). Modos Review (PASS/FAIL), Challenge e Consult. Complementa o gate de segurança do QA; nunca aprova sozinho.

Quando: antes de liberar algo sensível.

karvey-health

qualidade

Uma nota de qualidade de 0 a 10 (type-check, lint, testes, código morto) com tendência, mais a prontidão do método: skills instaladas e inputs fixados (repo path @commit) ainda vigentes.

Quando: revisões periódicas ou trabalho multirrepositório.

karvey-devex

revisão

Revisa a experiência do desenvolvedor: percorre o onboarding real, mede o time-to-hello-world e encontra atritos e “docs que mentem”. Modos plano e ao vivo.

Quando: ao auditar o onboarding ou a DX.

karvey-retro

revisão

Retrospectiva do ciclo: velocidade, saúde dos testes, detalhamento por pessoa, sequências e oportunidades de melhoria a partir do histórico de commits.

Quando: ao fechar um ciclo (recomendado no arquivamento).

karvey-browse

olhos

08 · O que roda sozinho e o que você escolhe

Hooks

Uma skill é orientação: o modelo a segue voluntariamente e ela não garante nada. Um hook bloqueia de verdade. O Karvey separa o que vem ativo com o plugin do que cada projeto decide ativar.

Ativo na instalação

automático SessionStart · karvey-session-context.sh (em startup|resume|compact|clear, timeout de 10 s).

  • Reinjeta identidade, manifesto, quadro, checklist e handoff (procura docs/spec/team.json, um .ceo-agentes legado ou docs/spec/agent/).
  • Mede: para cada repositório em state.json, compara branch, último commit e mudanças não commitadas contra a árvore viva → matches ou DRIFT — branch X -> Y.
  • Diz para rodar /karvey-checkpoint restore primeiro se houver uma mudança ativa, drift ou nenhum handoff.
  • 3.10 Num projeto Karvey sem configuração da equipe, imprime uma linha apontando para /karvey:karvey-init --settings.
  • Fora de um projeto Karvey é inerte: não imprime nada e sai com 0. Os hooks do plugin se somam aos seus; não os substituem.

à mão, uma vez Statusline · karvey-statusline.sh: contexto, limites da conta com a hora do próximo reset e o tempo restante de cada janela (ex.: 5h 29% ↻18:05 (1h31m) · 7d 35% ↻jue 21:20 (2d4h), relógio conforme KARVEY_TZ, por padrão o fuso horário do sistema), horas, custo e um aviso de “HORA DE ROTACIONAR”. Um plugin não pode declarar uma statusline, então você a cola no seu ~/.claude/settings.json. Roda fora do turno (não gasta tokens) e precisa de bash + python3.

{
  "statusLine": {
    "type": "command",
    "command": "bash ~/.claude/plugins/<marketplace>/karvey/<version>/hooks/karvey-statusline.sh",
    "padding": 0
  }
}

Limiares: KARVEY_ROTATE_CTX_YELLOW (100000), KARVEY_ROTATE_CTX_RED (150000), KARVEY_ROTATE_HOURS (8). Os 150k vêm de medição: com 588k de contexto, um turno custa 7× o que custa com 80k.

10 · Entrega

Deploy e branches

O deploy é disparado pelo pipeline, nunca à mão por uma pessoa ou por um agente: um push em dev faz o deploy de dev; um merge em master faz o deploy de prod. Os nomes vêm de project.json:branch_flow.

  1. feature/{change-id}Desenvolvimento e um commit por tarefa. Nunca commitar em dev ou master.
  2. devpull → merge → push ⇒ pipeline DEV → canary.
  3. PR dev → masterpull antes; os gates do PR (CI + políticas de branch) verdes.
  4. masterMerge só com OK humano ⇒ pipeline PROD → canary.
  5. HigieneBranches absorvidas apagadas (remoto + local); as não absorvidas são reportadas.

Checklist de 6 passos

  1. Estou numa feature branch?
  2. Atualizei o CHANGELOG.md?
  3. Commitei tudo o que estava pendente?
  4. Fiz push da branch?
  5. Fiz merge em dev?
  6. Fiz push de dev?

Só então o pipeline faz o deploy de dev. Para prod a verificação se repete, e o PR passa com aprovação.

Gates do PR e OK humano

O CI e as políticas de branch (build validation, revisores obrigatórios, status checks) rodam sobre o commit de merge e enxergam o que a verificação local não enxerga. Nunca se pede aprovação com um gate vermelho: isso transforma a aprovação num carimbo. Pular uma política é decisão e responsabilidade do humano.

O OK fica registrado no git: approvals.prod = { by, date, ref: D-NN }. O gate de produção nunca é delegado a um agente.

Canary pós-deploy

Depois de cada deploy (dev e prod), várias iterações espaçadas contra o runtime real: console, desempenho, páginas/endpoints, com evidência. Em dev, uma regressão impede a promoção para prod; em prod, dispara um alerta e recomenda rollback, também via pipeline. Reforça o zero downtime.

Higiene de branches

A absorção é verificada: git branch -r --merged, git cherry e o teste de árvore com git merge-tree --write-tree (squash). Absorvida → apagada (git branch -d, nunca -D). Não absorvida → nunca é apagada: é reportada com seus commits e o humano decide. As contagens são reportadas; nada é limpo em silêncio.

Bump de versão e versão visível

Cada deploy incrementa a versão (semver major.minor.rev, nunca reutilizada) e adiciona a entrada no CHANGELOG.md, por componente e por repositório. O front a exibe conforme o ambiente: DEV mostra a versão de desenvolvimento v3.10.1-dev.42+74571ae com a marca DEV; PROD mostra a versão de release v3.10.1.

A versão é lida do arquivo de versão (package.json, pyproject.toml…) no build — nunca de uma variável do pipeline, que fica desatualizada em silêncio. O pipeline só fornece ambiente, número do build e commit. O canary verifica se a versão visível corresponde ao ambiente.

Multirrepositório: o fluxo se aplica em cada repositório seguindo a ordem de dependências do architecture.md (ex.: DB → backend → frontend). Semver + CHANGELOG antes do push; versão visível no frontend (recomendado).

11 · Opcional

Camada de equipe de agentes

O pipeline carrega o eixo do trabalho; esta camada acrescenta o eixo de quem trabalha: quem o carrega, que papel tem, como sobrevive a um reset de contexto e como vários se coordenam sem pisar uns nos outros. É opt-in e não é o padrão recomendado. Sem docs/spec/team.json, a camada não existe para o projeto.

Um aviso honesto de custo (medido, não teórico). A execução que deu origem à regra: uma equipe de 6 agentes num produto real, 3 dias, ≈ US$1.000, e terminou voltando a um único agente com boas instruções. Um turno com 588k de contexto custou 7× um com 80k; 31% dos turnos responderam por 48% do gasto. Cada salto entre agentes é contexto novo para quem recebe: não há cache compartilhado entre sessões, e o mesmo pano de fundo é relido e pago de cada lado.

Não use uma equipe quando…

  • o orçamento importa;
  • o trabalho cabe num único contexto;
  • a divisão seria por tema, e não por repositório com dono real;
  • ninguém está medindo o gasto.

Ela compensa o custo com…

  • trabalho realmente paralelo em repositórios separados;
  • frentes de trabalho longas e independentes;
  • papéis que precisam de outras ferramentas ou permissões (uma máquina com navegador, um console operado por uma pessoa).

Se estiver ligada, meça

karvey-team cost grava o relatório no repositório. Também: init (mostra a tabela de custos e confirma antes de gravar), census (um inventário, não uma agenda de contatos) e relay (sessões prontas para rotacionar). Rotação por limiar: 150k de contexto ou 24 h por padrão.

O handoff e o hook de sessão funcionam igual com um único agente (docs/spec/agent/); com uma equipe, só muda o local ({ops_repo}/agents/<rol>/).

Karvey ist eine Methode für spezifikationsgetriebene Entwicklung (SDD) für Claude Code. Sie führt eine Änderung von der Idee bis in die Produktion – über eine Pipeline mit 13 Phasen (0–12) und Freigabe-Gates sowie eine Unterstützungsebene aus Skills, die jederzeit aufgerufen werden können. Sie ist stack-agnostisch (Web, iOS/Android, Desktop, CLI, API, Embedded) und funktioniert als Spirale, nicht als Linie: Was beim Testen, in der QA oder in der realen Laufzeitumgebung auftaucht, fließt dorthin zurück, wo es hingehört – so geht nichts verloren.

Diese Seite ergänzt die README des Repos: Sie erklärt die Denkweise der Methode und zeichnet die vollständige Landkarte des Plugins.

02 · Prinzipien

Denkweise

Sieben Ideen tragen die gesamte Methode. Jeder Skill und jede Regel ist die konkrete Ausprägung einer davon.

  1. SpezifikationsgetriebenJede Änderung beginnt mit einem PRD (prd.md); EARS-Anforderungen verweisen darauf zurück, und die Living Specs sammeln pro Capability, was das System tut.
  2. Stack-agnostischDas Projekt deklariert seine targets, und jede Phase passt sich an: Das Mockup einer CLI ist ein Befehlstranskript, das einer API sind Request/Response-Beispiele.
  3. Freigabe-GatesJede Phase erzeugt ein Dokument in docs/spec/ und bittet um Ihr OK, bevor es weitergeht. --autoplan bündelt die Planungs-Gates; es überspringt sie nicht.
  4. Spirale, nicht LinieDie Pipeline ist der Happy Path. Befunde kommen über drei Kanten zurück (bug, spec-gap, emergent), und eine Änderung ist erst fertig, wenn sie konvergiert.
  5. Nichts bleibt offenEin verpflichtendes Abschlussritual für jede Phase und Aufgabe, ein Discovery-Backlog, ein BUG-NN-Tracker und das Aufräumen aufgenommener Branches: Nichts geht verloren.
  6. Menschliches OK für die ProduktionDer Merge in den Produktions-Branch erfordert eine ausdrückliche Freigabe, festgehalten in approvals.prod. Sie wird nie an einen Agenten delegiert, und es gibt nie ein manuelles Deployment.
  7. Gemessen, nicht erinnertBerichtet wird nur, was in der Sitzung verifiziert wurde – mit Befehl und Nachweis. Die Übergabe wird mit Befehlen erfasst, und der Sitzungs-Hook prüft den gespeicherten Zustand gegen die Live-Repos.

12

Archivierung

/karvey:karvey-archive <change-id>
Was sie tut
Führt die Spec-Deltas in die Living Specs zusammen, archiviert die Änderung und schließt das Epic. Durchkämmt das Backlog (bietet an, emergent-Punkte zu neuen change-ids hochzustufen) und die Branches. Empfohlen: karvey-retro + karvey-docs.
Ergebnis
Ein aktualisiertes specs/{capability}/spec.md, changes/archive/{fecha}-{change-id}/.
Regeln
living-specsbacklogphase-closedeploy-workflow

Gate: Vollständigkeitsprüfung; die Änderung wird nicht geschlossen, solange einer ihrer Branches noch existiert.

Änderungstypen: feature, ops, hotfix und übergeordnete Änderung
  • ops (IAM, DNS, Secrets, Konsole): init → requirements (lite) → infra (command plan) → tasks ([human]/[Infra]) → execution + verification → archive. Mockup, Design und Architektur entfallen (Letztere nur, sofern sich keine Vertrauensgrenzen ändern).
  • hotfix: iterate (BUG-NN) → impl → test (regression) → deploy, mit Fix + BUG-NN + Regressionstest im selben PR. Die Anforderungen werden nur wieder geöffnet, wenn der Defekt ein spec-gap ist.
  • Übergeordnete Änderung (links.children): hat keinen eigenen Code; zeigt die Phase jedes Kindes ({change-id}@{repo}) und wechselt erst auf deployed, wenn jedes Kind deployt oder per Entscheidung verworfen ist.
  • Reiner Dokumentations-PR: leichtgewichtige CI (Spec-Lint) statt Build/Test/Deploy; löst nie ein Deployment aus.

06 · Jederzeit

Unterstützungsebene · 18 Unterstützungs-Skills

Sie sind keine Phasen: Sie schieben spec.json:phase nicht voran. Die einzige Ausnahme ist karvey-iterate, das den kontrollierten Übergang zurück im Revisions-Teilzyklus vornehmen darf. Sie respektieren dieselben Gates und Hooks.

karvey-iterate

Iteration

Der Iterationsmotor: liest findings.md, bestätigt den Typ und leitet jeden Befund an bug, spec-gap oder emergent weiter. Der einzige Ort, an dem die Logik der Schleife lebt.

Wann: wenn Befunde aufgetaucht sind oder sich die Spezifikation als falsch oder unvollständig erwiesen hat.

karvey-investigate

Diagnose

Debugging bis zur Grundursache. Eisernes Gesetz: kein Fix ohne Untersuchung. Datiert das Symptom, fragt, was sich geändert hat, bevor es fragt, was falsch ist, verfolgt die Daten über Repos hinweg und trennt die Ursache von latenter Fragilität.

Wann: wenn etwas fehlschlägt und niemand versteht, warum.

karvey-second-opinion

Review

Adversariales Review mit einem anderen Modell (Claude vs. GPT/Codex/Gemini). Modi Review (PASS/FAIL), Challenge und Consult. Ergänzt das Sicherheits-Gate der QA; gibt nie eigenständig frei.

Wann: bevor etwas Heikles veröffentlicht wird.

karvey-health

Qualität

Ein Qualitätswert von 0–10 (Type-Check, Lint, Tests, toter Code) mit Trend, dazu die Methodenbereitschaft: installierte Skills und gepinnte Eingaben (repo path @commit), die noch aktuell sind.

Wann: regelmäßige Kontrollen oder Arbeit über mehrere Repos.

karvey-devex

Review

Prüft die Developer Experience: durchläuft das reale Onboarding, misst die Time-to-Hello-World und findet Reibungspunkte und „Dokumentation, die lügt“. Modi Plan und Live.

Wann: beim Audit von Onboarding oder DX.

karvey-retro

Review

Retrospektive eines Zyklus: Velocity, Testgesundheit, Aufschlüsselung pro Person, Serien und Verbesserungsmöglichkeiten aus der Commit-Historie.

Wann: beim Abschluss eines Zyklus (empfohlen bei der Archivierung).

karvey-browse

Augen

Gibt dem Agenten Augen in der realen Laufzeitumgebung: Browser (Web), Simulator oder Gerät (Mobile), Terminal (CLI). Klicken, Screenshot, Inspizieren; importiert Cookies für authentifizierte Ansichten.

Wann: um zu sehen, was der Nutzer sieht; schreibt ebenfalls in findings.md.

karvey-checkpoint

Zustand / Übergabe

save / restore des Checkpoints der Änderung und der Übergabe des Agenten: Identität, Manifest, Board, Checkliste, gemessener Repo-Zustand (state.json), stehende Entscheidungen und geplante Aufgaben.

Wann: beim Rotieren einer Sitzung oder bei der Übergabe von Arbeit, mit einem oder mehreren Agenten.

karvey-docs

Dokumentation

Dokumentationsingenieur: erzeugt Diátaxis-Dokumentation (Tutorial, How-to, Referenz, Erklärung) aus dem Code, aktualisiert veraltete Dokumentation und exportiert Markdown als PDF.

Wann: nach einem Release (empfohlen bei der Archivierung).

karvey-diagram

Diagramme

Natürliche Sprache zu Diagramm: Mermaid-Quelltext + editierbares .excalidraw + gerendertes SVG/PNG. Funktioniert offline.

Wann: Ablauf, Sequenz, Architektur oder ER.

karvey-guard

Leitplanken

Installiert oder entfernt die Enforcement-Hooks, gewährt einen temporären Plan-Gate-Override, legt einen Edit-Lock auf ein Verzeichnis (--freeze) und führt die Verifikations-Checkliste aus (--verify, nur lesend).

Wann: bei heikler Arbeit oder um den Ablauf durchzusetzen.

karvey-team

Team · optional

Opt-in-Teamebene: init, census, relay, cost. Rollen, Manifeste, Boards, Zensus, Ablösung und Kostenmessung.

Wann: erst nach dem Lesen von rules/team.md; Karvey ist mit einem einzigen Agenten vollständig.

karvey-decisions

Team · Entscheidungen

Ein einziges nummeriertes Register (D-NN fachlich, C-NN Ausrichtung), auf das sich Änderungen beziehen. cross prüft eine Frage gegen das Register, bevor irgendetwas als blockiert erklärt wird.

Wann: beim Treffen, Nachschlagen oder Zitieren einer Entscheidung.

08 · Was von selbst läuft und was Sie wählen

Hooks

Ein Skill ist eine Anleitung: Das Modell befolgt sie freiwillig, und sie garantiert nichts. Ein Hook blockiert tatsächlich. Karvey trennt, was mit dem Plugin aktiv ausgeliefert wird, von dem, was jedes Projekt zu aktivieren beschließt.

Aktiv bei Installation

automatisch SessionStart · karvey-session-context.sh (bei startup|resume|compact|clear, Timeout 10 s).

  • Injiziert Identität, Manifest, Board, Checkliste und Übergabe erneut (sucht nach docs/spec/team.json, einem älteren .ceo-agentes oder docs/spec/agent/).
  • Misst: Für jedes Repo in state.json vergleicht er Branch, letzten Commit und nicht committete Änderungen mit dem Live-Stand → matches oder DRIFT — branch X -> Y.
  • Fordert auf, zuerst /karvey-checkpoint restore auszuführen, wenn es eine aktive Änderung, Drift oder keine Übergabe gibt.
  • 3.10 In einem Karvey-Projekt ohne Team-Einstellungen gibt er eine Zeile mit Verweis auf /karvey:karvey-init --settings aus.
  • Außerhalb eines Karvey-Projekts ist er inaktiv: gibt nichts aus und beendet sich mit 0. Die Hooks des Plugins ergänzen Ihre eigenen; sie ersetzen sie nicht.

von Hand, einmalig Statusline · karvey-statusline.sh: Kontext, Kontolimits mit Uhrzeit des nächsten Resets und verbleibender Zeit für jedes Fenster (z. B. 5h 29% ↻18:05 (1h31m) · 7d 35% ↻jue 21:20 (2d4h), Uhrzeit gemäß KARVEY_TZ, standardmäßig die Zeitzone des Systems), Stunden, Kosten und eine Warnung „TIME TO ROTATE“. Ein Plugin kann keine Statusline deklarieren, deshalb fügen Sie sie in Ihre ~/.claude/settings.json ein. Sie läuft außerhalb des Turns (kostet keine Tokens) und benötigt bash + python3.

{
  "statusLine": {
    "type": "command",
    "command": "bash ~/.claude/plugins/<marketplace>/karvey/<version>/hooks/karvey-statusline.sh",
    "padding": 0
  }
}

Schwellenwerte: KARVEY_ROTATE_CTX_YELLOW (100000), KARVEY_ROTATE_CTX_RED (150000), KARVEY_ROTATE_HOURS (8). Die 150k stammen aus Messungen: Bei 588k Kontext kostet ein Turn das 7-Fache dessen, was er bei 80k kostet.

Optional pro Projekt

Opt-in karvey-init fragt, ob sie aktiviert werden sollen (Schritt 3.5), und karvey-guard verwaltet sie anschließend. Sie werden in die settings.json des Projekts geschrieben, parametrisiert mit branch_flow. Nie global auferlegt.

10 · Auslieferung

Deploy und Branches

Das Deployment wird von der Pipeline ausgelöst, nie von Hand durch eine Person oder einen Agenten: Ein Push auf dev deployt dev; ein Merge nach master deployt prod. Die Namen stammen aus project.json:branch_flow.

  1. feature/{change-id}Entwicklung und ein Commit pro Aufgabe. Nie auf dev oder master committen.
  2. devpull → merge → push ⇒ DEV-Pipeline → Canary.
  3. PR dev → masterzuerst pull; die Gates des PR (CI + Branch-Policies) grün.
  4. masterMerge nur mit menschlichem OK ⇒ PROD-Pipeline → Canary.
  5. HygieneAufgenommene Branches gelöscht (remote + lokal); nicht aufgenommene werden gemeldet.

6-Schritte-Checkliste

  1. Bin ich auf einem Feature-Branch?
  2. Habe ich CHANGELOG.md aktualisiert?
  3. Habe ich alles Ausstehende committet?
  4. Habe ich den Branch gepusht?
  5. Habe ich nach dev gemergt?
  6. Habe ich dev gepusht?

Erst dann deployt die Pipeline dev. Für prod wird die Prüfung wiederholt, und der PR geht mit Freigabe durch.

PR-Gates und menschliches OK

CI und Branch-Policies (Build-Validierung, erforderliche Reviewer, Status-Checks) laufen auf dem Merge-Commit und sehen, was die lokale Prüfung nicht sieht. Bei einem roten Gate wird nie um Freigabe gebeten: Das macht die Freigabe zum bloßen Abnicken. Eine Policy zu überspringen ist Entscheidung und Verantwortung des Menschen.

Das OK wird in git festgehalten: approvals.prod = { by, date, ref: D-NN }. Das Produktions-Gate wird nie an einen Agenten delegiert.

Canary nach dem Deployment

Nach jedem Deployment (dev und prod) mehrere zeitlich versetzte Durchläufe gegen die reale Laufzeitumgebung: Konsole, Performance, Seiten/Endpunkte, mit Nachweisen. In dev stoppt eine Regression die Promotion nach prod; in prod löst sie einen Alarm aus und empfiehlt einen Rollback, ebenfalls per Pipeline. Das stärkt Zero Downtime.

Branch-Hygiene

Die Aufnahme wird verifiziert: git branch -r --merged, git cherry und der Tree-Test mit git merge-tree --write-tree (Squash). Aufgenommen → gelöscht (git branch -d, nie -D). Nicht aufgenommen → nie gelöscht: Er wird mit seinen Commits gemeldet, und der Mensch entscheidet. Zahlen werden berichtet; nie wird stillschweigend aufgeräumt.

Versionssprung und sichtbare Version

Jedes Deployment erhöht die Version (Semver major.minor.rev, nie wiederverwendet) und ergänzt den Eintrag in CHANGELOG.md, pro Komponente und pro Repository. Ein Frontend zeigt sie je nach Umgebung: DEV zeigt die Entwicklungsversion v3.10.1-dev.42+74571ae mit einer DEV-Markierung; PROD zeigt die Release-Version v3.10.1.

Die Version wird beim Build aus der Versionsdatei gelesen (package.json, pyproject.toml …) — nie aus einer Pipeline-Variablen, die unbemerkt veraltet. Die Pipeline liefert nur Umgebung, Build-Nummer und Commit. Der Canary prüft, ob die sichtbare Version zur Umgebung passt.

Mehrere Repos: Der Ablauf gilt in jedem Repo gemäß der Abhängigkeitsreihenfolge in architecture.md (z. B. DB → Backend → Frontend). Semver + CHANGELOG vor dem Push; Version im Frontend sichtbar (empfohlen).

11 · Optional

Agententeam-Ebene

Die Pipeline trägt die Achse der Arbeit; diese Ebene fügt die Achse des Arbeitenden hinzu: wer sie trägt, welche Rolle er hat, wie er einen Kontext-Reset übersteht und wie sich mehrere abstimmen, ohne sich gegenseitig in die Quere zu kommen. Sie ist Opt-in und nicht der empfohlene Standard. Ohne docs/spec/team.json existiert die Ebene für das Projekt nicht.

Eine ehrliche Kostenwarnung (gemessen, nicht theoretisch). Der Durchlauf, aus dem die Regel entstand: ein Team aus 6 Agenten an einem realen Produkt, 3 Tage, ≈ 1.000 US$ – und am Ende die Rückkehr zu einem einzigen Agenten mit guten Anweisungen. Ein Turn bei 588k Kontext kostete das 7-Fache eines Turns bei 80k; 31 % der Turns verursachten 48 % der Kosten. Jeder Sprung zwischen Agenten ist frischer Kontext für den Empfänger: Es gibt keinen sitzungsübergreifenden gemeinsamen Cache, und derselbe Hintergrund wird auf jeder Seite erneut gelesen und bezahlt.

Kein Team verwenden, wenn…

  • das Budget eine Rolle spielt;
  • die Arbeit in einen Kontext passt;
  • die Aufteilung nach Thema statt nach Repo mit echtem Verantwortlichen erfolgen würde;
  • niemand die Kosten misst.

Es lohnt sich bei…

  • wirklich paralleler Arbeit in getrennten Repos;
  • langen, unabhängigen Arbeitssträngen;
  • Rollen, die andere Werkzeuge oder Berechtigungen brauchen (eine Maschine mit Browser, eine von einem Menschen bediente Konsole).

Wenn aktiv, dann messen

karvey-team cost schreibt den Bericht ins Repo. Außerdem: init (zeigt die Kostentabelle und bestätigt vor dem Schreiben), census (ein Inventar, kein Adressbuch) und relay (Sitzungen, die zur Rotation bereit sind). Rotation nach Schwellenwert: standardmäßig 150k Kontext oder 24 h.

Übergabe und Sitzungs-Hook funktionieren mit einem einzigen Agenten genauso (docs/spec/agent/); mit einem Team ändert sich nur ihr Ort ({ops_repo}/agents/<rol>/).

Karvey 是一套面向 Claude Code 的规格驱动开发（SDD）方法。它通过一条带审批关卡的 13 阶段流水线（0–12），把一项变更从想法带到生产环境，另外还有一个可随时调用的技能支持层。它与技术栈无关（Web、iOS/Android、桌面、CLI、API、嵌入式），并且以螺旋而非直线的方式运作：测试、QA 或真实运行环境中发现的任何问题，都会回到它该去的地方，不会有任何遗漏。

本页是对仓库 README 的补充：它说明这套方法的思考方式，并绘出插件的完整地图。

02 · 原则

思考方式

七个理念支撑起整套方法。每个技能、每条规则都是其中某个理念的具体体现。

  1. 规格驱动每项变更都从一份 PRD（prd.md）开始；EARS 需求可追溯到它，而活规格按能力逐步累积系统所做的事情。
  2. 技术栈无关项目声明自己的 targets，每个阶段随之调整：CLI 的原型是一段命令记录；API 的原型则是请求/响应示例。
  3. 审批关卡每个阶段都会在 docs/spec/ 中产出一份文档，并在继续之前征求你的同意。--autoplan 会把规划阶段的关卡批量处理，但不会跳过它们。
  4. 螺旋，而非直线流水线只是理想路径。发现的问题会沿三条边（bug、spec-gap、emergent）回流，变更只有在收敛后才算就绪。
  5. 不留悬而未决每个阶段和任务都有强制的收尾仪式，还有发现待办清单、BUG-NN 追踪表以及对已合入分支的清理：没有任何遗漏。
  6. 上线须人工批准合并到生产分支需要明确批准，并记录在 approvals.prod 中。这一步从不委托给代理，也从不手动部署。
  7. 靠测量，不靠记忆只报告在本次会话中验证过的内容，并附上命令和证据。交接用命令捕获，会话 hook 会将保存的状态与实时仓库进行比对。

变更类型：feature、ops、hotfix 与父变更

05 · 螺旋

迭代循环

Afán——热忱：在真正达成结果之前不停下。test、qa 和 browse 只负责观察和分类（记录到 findings.md）；只有 karvey-iterate 负责路由。

发现项类型及其对应的边
类型判别标准边是否阻断？
bug“规格是对的，代码错了。”带状态历史的 BUG-NN 追踪表（DETECTADO → DIAGNOSTICADO → EN FIX → RESUELTO → REABIERTO，即已发现、已诊断、修复中、已解决、已重开）→ impl→test→qa 微循环。是，直至解决。
spec-gap“如果当初规格写对了，实现就会不一样。”修订子循环：approvals.requirements 置为 false，iteration_count +1，在 revision_history 中新增一条记录；只修订并重新批准受影响的需求。是，直至解决。
emergent“好主意，但那是另一项变更。”docs/spec/backlog.md（事实来源）+ 追踪工具中的镜像 → 在归档清扫时成为新的 change-id。否；只需记录下来。

06 · 随时可用

支持层 · 18 个支持技能

它们不是阶段：不会推进 spec.json:phase。唯一的例外是 karvey-iterate，它可以执行修订子循环中受控的回退转换。它们同样遵守关卡和 hooks。

karvey-iterate

迭代

迭代引擎：读取 findings.md，确认类型，并把每个发现项路由到 bug、spec-gap 或 emergent。循环逻辑只存在于这一处。

何时用：出现了发现项，或规格被证明有误或不完整。

karvey-investigate

诊断

根因调试。铁律：不调查，不修复。先确定症状出现的时间，先问“变了什么”再问“哪里错了”，跨仓库追踪数据，并把根因与潜在的脆弱点区分开。

何时用：某处出错而没人明白原因。

karvey-second-opinion

评审

用另一个模型进行对抗式评审（Claude 对比 GPT/Codex/Gemini）。提供 Review（PASS/FAIL）、Challenge 和 Consult 三种模式。它是对 QA 安全关卡的补充；从不单独批准。

何时用：发布敏感内容之前。

karvey-health

质量

0–10 的质量评分（类型检查、lint、测试、死代码）及其趋势，外加方法就绪度：技能已安装，且固定的输入（repo path @commit）仍是最新。

何时用：定期体检或多仓库工作。

karvey-devex

评审

评审开发者体验：走一遍真实的上手流程，测量 time-to-hello-world，找出摩擦点和“说谎的文档”。提供计划和实时两种模式。

何时用：审查上手流程或 DX。

karvey-retro

评审

08 · 哪些自动运行，哪些由你选择

Hooks

技能只是指引：模型自愿遵循，不提供任何保证。hook 才能真正阻断。Karvey 把随插件自动启用的部分，与每个项目自行决定启用的部分区分开来。

安装即生效

自动 SessionStart · karvey-session-context.sh（在 startup|resume|compact|clear 时触发，超时 10 秒）。

  • 重新注入身份、清单、看板、检查表和交接（查找 docs/spec/team.json、旧版的 .ceo-agentes 或 docs/spec/agent/）。
  • 测量：对 state.json 中的每个仓库，将分支、最后一次提交和未提交的更改与实时工作树比对 → matches 或 DRIFT — branch X -> Y。
  • 如果有进行中的变更、存在漂移或没有交接，会提示先运行 /karvey-checkpoint restore。
  • 3.10 在没有团队设置的 Karvey 项目中，会打印一行提示，指向 /karvey:karvey-init --settings。
  • 在 Karvey 项目之外它不起作用：什么也不打印，以 0 退出。插件的 hooks 是对你已有 hooks 的补充，而不是替换。

手动，一次即可 状态栏 · karvey-statusline.sh：上下文、账户限额，并显示每个时间窗口下一次重置的时间和剩余时间（例如 5h 29% ↻18:05 (1h31m) · 7d 35% ↻jue 21:20 (2d4h)，时钟依据 KARVEY_TZ，默认为系统时区）、时长、成本以及“该轮换了”（TIME TO ROTATE）警告。插件无法声明状态栏，所以需要你把它粘贴到自己的 ~/.claude/settings.json 中。它在对话轮次之外运行（不消耗 token），需要 bash + python3。

{
  "statusLine": {
    "type": "command",
    "command": "bash ~/.claude/plugins/<marketplace>/karvey/<version>/hooks/karvey-statusline.sh",
    "padding": 0

}

阈值：KARVEY_ROTATE_CTX_YELLOW（100000）、KARVEY_ROTATE_CTX_RED（150000）、KARVEY_ROTATE_HOURS（8）。150k 来自实测：上下文达到 588k 时，一轮的成本是 80k 时的 7 倍。

10 · 交付

部署与分支

部署由流水线触发，绝不由人或代理手动执行：push 到 dev 部署 dev；合并到 master 部署 prod。分支名称来自 project.json:branch_flow。

  1. feature/{change-id}开发，每个任务一次提交。绝不在 dev 或 master 上提交。
  2. devpull → merge → push ⇒ DEV 流水线 → canary。
  3. PR dev → master先 pull；PR 的关卡（CI + 分支策略）全绿。
  4. master只有经人工批准才合并 ⇒ PROD 流水线 → canary。
  5. 清理已合入的分支被删除（远程 + 本地）；未合入的分支会被报告。

6 步检查表

  1. 我在 feature 分支上吗？
  2. 我更新了 CHANGELOG.md 吗？
  3. 所有待提交的内容都提交了吗？
  4. 我 push 了分支吗？
  5. 我合并到 dev 了吗？
  6. 我 push 了 dev 吗？

只有这样，流水线才会部署 dev。对于 prod，会重复验证，PR 经批准后才能通过。

PR 关卡与人工批准

CI 和分支策略（构建验证、必需评审人、状态检查）在合并提交上运行，能看到本地检查看不到的东西。关卡为红时绝不请求批准：那会让批准沦为橡皮图章。跳过某项策略是人的决定，也是人的责任。

批准记录在 git 中：approvals.prod = { by, date, ref: D-NN }。生产关卡从不委托给代理。

部署后 canary

每次部署之后（dev 和 prod），针对真实运行环境进行多轮间隔执行的检查：控制台、性能、页面/端点，并附证据。在 dev 中出现回归会阻止升级到 prod；在 prod 中则会发出告警并建议回滚，回滚同样通过流水线进行。它强化了零停机。

分支清理

是否已合入需经过验证：git branch -r --merged、git cherry，以及用 git merge-tree --write-tree 做的树测试（针对 squash）。已合入 → 删除（git branch -d，绝不用 -D）。未合入 → 绝不删除：连同其提交一起报告，由人决定。会报告数量；从不悄悄清理任何东西。

版本递增与可见版本

每次部署都会递增版本号（语义化版本 major.minor.rev，绝不复用），并按组件、按仓库在 CHANGELOG.md 中添加条目。前端按环境显示版本：DEV 显示开发版本 v3.10.1-dev.42+74571ae 并带有 DEV 标记；PROD 显示发布版本 v3.10.1。

版本号在构建时从版本文件（package.json、pyproject.toml 等）读取——绝不取自流水线变量，因为它会悄无声息地过时。流水线只提供环境、构建号和提交。金丝雀检查会核对可见版本是否与环境相符。

多仓库：该流程按照 architecture.md 中的依赖顺序在每个仓库中执行（例如 DB → backend → frontend）。push 之前完成 Semver + CHANGELOG；建议在前端显示版本号。

代理团队层

流水线承载的是工作这条轴线；这一层增加的是执行者这条轴线：由谁承担、担任什么角色、如何熬过上下文重置，以及多个代理如何协调而互不干扰。它需主动启用，并非推荐的默认选项。没有 docs/spec/team.json 时，这一层对该项目来说就不存在。

一则坦诚的成本警告（实测所得，而非理论）。催生这条规则的那次运行：一个 6 人代理团队用于一个真实产品，历时 3 天，花费约 1,000 美元，最终回到了单个代理加良好指令的方式。上下文 588k 时一轮的成本是 80k 时的 7 倍；31% 的轮次占了 48% 的开销。代理之间的每一次传递，对接收方来说都是全新的上下文：会话之间没有共享缓存，同样的背景信息在每一方都要被重新读取并付费。

以下情况不要用团队……

  • 预算很重要；
  • 工作能放进一个上下文；
  • 拆分依据是主题，而不是有真正负责人的仓库；
  • 没人在测量开销。

以下情况物有所值……

  • 在不同仓库中真正并行的工作；
  • 长期、相互独立的工作流；
  • 需要其他工具或权限的角色（带浏览器的机器、由人操作的控制台）。

如果启用，就要测量

karvey-team cost 会把报告写入仓库。此外还有：init（显示成本表并在写入前确认）、census（一份清点，而非通讯录）和 relay（可轮换的会话）。按阈值轮换：默认为 150k 上下文或 24 小时。

交接和会话 hook 在单个代理下同样有效（docs/spec/agent/）；有团队时只是位置不同（{ops_repo}/agents/<rol>/）。

12 · 开始使用

安装与更新

安装（在 Claude Code 内）

/plugin marketplace add MauricioQuezadaHaintech/karvey
/plugin install karvey@karvey-methods

更新（终端）

claude plugin marketplace update karvey-methods
claude plugin update karvey@karvey-methods

然后运行 /reload-plugins 或重启会话以加载新版本。用 claude plugin list（或 /plugin）检查。

首次使用

/karvey:karvey-grill        # 规格前访谈
/karvey:karvey-init <id>    # 创建变更 + 团队设置
/karvey:karvey <id>         # 状态与下一步
/karvey:karvey-context      # 项目仪表盘
