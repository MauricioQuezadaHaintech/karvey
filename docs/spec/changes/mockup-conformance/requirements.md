# Requirements: mockup-conformance

## Project description

What is built matches the approved mockup, one to one (D-40, release 4.3.0). Four parts: (1) every element of a
mockup carries a stable element id and the requirements it covers, and every decision taken while iterating the
mockup is written back into the requirements before the mockup can be approved; (2) the approved mockup, frozen by
its hash, is a mandatory input of implementation, which builds from its structure and styles and keeps the same
element ids; (3) a blocking conformance gate checks that every mockup element exists in the build, compares
side-by-side captures of mockup and build at the same viewport and state with the differences marked (pixel
difference with a threshold where the target allows), and holds QA, the release gate and deploy until every
difference is fixed or recorded as a deviation the owner approved through the hook; (4) a traceability matrix
requirement → mockup element → test → evidence is complete before release. Web, mobile, desktop and CLI targets are
defined; every other target is scoped out by name. North star (PRD §2): *the UI a change ships is the UI the owner
approved in its mockup.*

## Conventions

- **IDs.** `REQ-MC-NNN`; requirements added after the judges' review take the next free number (054…) and sit in
  their area. The heading also carries the numeric EARS id (`1.1`, `1.2`…).
- **Trace line.** Each requirement cites the PRD (`PRD §n`, scope `S-n`, objective `O-n`, acceptance `AC-n`), its
  decisions (`D-NN`) and the living requirements it builds on (`REQ-W1-*`, `REQ-W2-*`, `REQ-W3-*`, `REQ-UP-*`,
  `REQ-LD-*`).
- **Living spec baseline.** The blocks of `wave1-hardening`, `wave2-structural`, `project-upgrade`,
  `wave3-optimization` and `living-docs` are treated as already part of the living spec. A requirement that changes
  one of them says **MODIFIES REQ-…**; `spec-delta.md` lists it under MODIFIED.
- **Modes.** As in Waves 2 and 3 and `living-docs`: **advisory**, **warn** or **blocking**. "In 4.3" means the
  default of release 4.3.0 in the check-mode registry (REQ-MC-049).
- **Actors.** "the owner" = the person who owns the change's approvals (`role: human`); "the agent" = any model
  session working on the change, including a browsing agent; "the hook" = the method's prompt hook, which runs
  outside the model (D-01); "the state tool" = the only writer of `spec.json` state; "a UI change" = a change whose
  lane runs the mockup phase and whose mockup was not skipped.
- **Reviewed line.** A setting read "from the reviewed line" is read from the project settings as committed on
  `origin/{production}`; the same key in the working copy is ignored and the audit log records
  `conformance setting ignored (not reviewed)` (the trust model of D-01, as in REQ-LD-011).
- **UI code.** The files a UI change's conformance depends on: the code paths of the frontend-module components in
  the component map (REQ-LD-019); else the globs of `conformance.ui_paths`; else every file outside `docs/`.
- **Surface of a requirement.** In a UI change every requirement declares `Surface: ui` (something a person sees or
  operates) or `Surface: none` on its trace line; the checks below use this field.
- **Technology.** SHALL text names roles of the method. Public names are in the glossary; browser automation, image
  comparison and parsers are architecture decisions, and any product appears only as one example among several.
- **Neutrality.** No requirement, rule, template or example names an organisation, product, client, person,
  internal URL or personal path; examples are fictional.

## Requirement 1: Element ids in the mockup (D-40 part 1)

### 1.1 REQ-MC-001 — Required elements carry an element id
WHERE a change is a UI change, the mockup skill SHALL give an element id to every mockup element of these kinds:
screen or view; overlay (dialog, drawer, menu, toast); region (a named area of a screen, such as a filter bar, a
table or a form section); control (button, link, input, select, toggle, tab); message (validation, error, empty,
success); and the container of each Level-4 state. A decorative element or a layout wrapper that no requirement
names SHALL NOT need one.

Traces to PRD: §6 S-1, O-1, AC-1 · Decision: D-40

**Scenario — success:** GIVEN a UI change whose mockup shows an invoice list with a filter bar, an export button and an
empty state WHEN the element check runs THEN each of the four carries an element id and no error is reported.
**Scenario — error:** GIVEN the same mockup with the export button lacking an element id WHEN the element check runs
THEN it reports `missing id: control` with the element's path in the document and exits non-zero.

### 1.2 REQ-MC-002 — Id format and uniqueness
An element id SHALL match `[a-z0-9]+(-[a-z0-9]+)*`, be at most 48 characters long, contain no run of 6 or more digits
and no match of the method's secret patterns, and be unique within the change's mockup,
except that the instances of a repeated element (list rows, cards) SHALL share one id and each carry the repeat
marker.

Traces to PRD: §6 S-1, §9, O-1, AC-1 · Decision: D-40

**Scenario — success:** GIVEN `invoice-row` on twenty rows, each with the repeat marker WHEN the element check runs
THEN it records one repeated element with twenty instances.
**Scenario — error:** GIVEN two different buttons both marked `export` and no repeat marker WHEN the element check runs
THEN it reports `duplicate id: export` with both paths; GIVEN an id `Export_Btn` THEN it reports `bad id format`; GIVEN
an id `row-4471823` THEN it reports `id carries a digit run`.

### 1.3 REQ-MC-003 — Each element names the requirements it covers
Every element with an element id SHALL carry the requirement attribute listing at least one requirement id of the
change or of the living spec, or the value `gap`; the element check SHALL report an unknown requirement id as an
error and an element marked `gap` as a spec-gap to route through the iteration skill (a requirement added or the
element removed).

Traces to PRD: §6 S-1, O-1, AC-1 · Decision: D-40 · Builds on: the mockup skill's spec↔mockup validation

**Scenario — success:** GIVEN `export` citing `REQ-INV-004` which exists in `requirements.md` WHEN the element check
runs THEN the element map records `export → REQ-INV-004`.
**Scenario — error:** GIVEN `export` citing `REQ-INV-099`, which does not exist WHEN the element check runs THEN it
reports `unknown requirement REQ-INV-099 on export`; GIVEN an element marked `gap` THEN it reports a spec-gap naming
the element.

### 1.4 REQ-MC-004 — Every UI requirement is covered; every cited one is UI
In a UI change, every requirement of the change SHALL declare its surface (`Surface: ui` or `Surface: none`) on its
trace line; the element check SHALL report every `ui` requirement of the change that no element cites and every
element that cites a `none` requirement of the change; a living-spec requirement cited by an element SHALL be treated
as `ui` for that element and SHALL NOT count in the change's coverage.

Traces to PRD: §6 S-1, O-1, AC-1 · Decision: D-40

**Scenario — success:** GIVEN five `ui` requirements each cited by at least one element and three `none` requirements
cited by none WHEN the element check runs THEN coverage is reported as 5/5.
**Scenario — error:** GIVEN `REQ-INV-007` (`Surface: ui`, "the export offers a date range") cited by no element WHEN
the element check runs THEN it reports `uncovered ui requirement REQ-INV-007`; GIVEN a requirement without a surface
THEN it reports `surface missing` for it.

### 1.5 REQ-MC-005 — The element check is deterministic and writes the element map
The element check SHALL read the change's mockup files, SHALL write the element map — for each id: its kind, the
screen and state it belongs to, its parent id, its order among siblings, its visible text, its requirement ids and
whether it repeats — and SHALL report every violation of REQ-MC-001 to REQ-MC-004 and REQ-MC-006 with the element's
path; for the same input it SHALL produce byte-identical output and SHALL exit non-zero while any error remains. The
mockup skill SHALL run it on every generated iteration and before presenting the mockup.

Traces to PRD: §6 S-1, O-1, AC-1 · Decision: D-40

**Scenario — success:** GIVEN an unchanged mockup WHEN the element check runs twice THEN the two element maps are
identical byte for byte.
**Scenario — error:** GIVEN a mockup file that does not parse WHEN the element check runs THEN it reports the file and
the position of the parse error, writes no element map and exits non-zero.
**Scenario — success (map content):** GIVEN `export` inside `filter-bar`, second among its siblings, with the text
"Export" WHEN the element check runs THEN the map records kind `control`, parent `filter-bar`, order 2, text "Export".
**Scenario — error (skill wiring):** GIVEN the mockup skill presenting an iteration WHEN no element-check output for that
iteration exists THEN the state tool refuses `generated mockup` with `element check not run`.

### 1.6 REQ-MC-006 — Ids are stable across iterations
Once an element id has appeared in a generated iteration of the change's mockup, it SHALL keep denoting an element of
the same kind on the same screen; the element check SHALL compare the new iteration with the previous element map and SHALL list removed ids,
SHALL accept a renamed id only when the element map records it as `old → new`, and SHALL refuse an id that was
removed in an earlier iteration and now denotes an element of another kind or screen.

Traces to PRD: §6 S-1, O-1 · Decision: D-40

**Scenario — success:** GIVEN iteration 2 renames `export` to `export-csv` with the rename recorded WHEN the element
check runs THEN it reports the rename and no error.
**Scenario — error:** GIVEN `export` removed in iteration 2 and reused in iteration 3 for an empty-state message WHEN
the element check runs THEN it reports `reused id export (control → message)` and exits non-zero.
**Scenario — success (removed):** GIVEN `print` present in iteration 1 and absent in iteration 2 WHEN the element check
runs THEN it lists `removed: print` in its output and in the element map.

### 1.7 REQ-MC-007 — Design-graphic keeps the ids
WHEN design-graphic updates the mockup with the visual system, it SHALL keep every element id, requirement attribute,
repeat marker and dynamic marker; the element check SHALL run after it, and the design approval SHALL be refused
while it reports a lost or changed id without a recorded rename.

Traces to PRD: §6 S-1, S-8, O-1 · Decision: D-40 · Builds on: REQ-W3-036

**Scenario — success:** GIVEN design-graphic restyles the invoice list WHEN the element check runs THEN the element map
has the same ids and requirements as at the mockup's approval.
**Scenario — error:** GIVEN design-graphic replaced the filter bar and dropped `filter-status` WHEN the design approval
is requested THEN the state tool refuses it naming `filter-status`.

## Requirement 2: Decisions written back (D-40 part 1)

### 2.1 REQ-MC-008 — Every iteration decision is logged
WHEN the owner gives feedback on a mockup iteration, the mockup skill SHALL record through the state tool, in the
decision log, one row per decision it applies — anything that changes a behaviour, a field, a state, a validation, a
text, an order or what is visible — with the iteration number, the owner's words (a short quote, or the instruction
row `F-NN` when instruction capture is on), the element ids affected and the status `unresolved`; a change the agent
makes on its own initiative (fixing a spec-gap, a restyle by design-graphic) SHALL be recorded the same way with origin
`agent`. The element check SHALL report every element added or removed, and every element whose text or requirement
attribute changed, between two iterations that no decision row cites.

Traces to PRD: §6 S-2, O-2, AC-2 · Decision: D-40

**Scenario — success:** GIVEN the owner says "the filter goes above the table and adds a status filter" WHEN the
mockup skill applies it THEN the decision log gains `MD-03` (iteration 2, elements `filter-bar`, `filter-status`,
status `unresolved`).
**Scenario — error:** GIVEN the agent writes a row into the decision log by editing the file WHEN the state tool next
validates the change THEN it reports the row as not written by the state tool and refuses the mockup approval.
**Scenario — error (unlogged change):** GIVEN iteration 3 changes the text of `export` to "Download" and no decision row
cites `export` WHEN the element check runs THEN it reports `unlogged change: export (text)`.

### 2.2 REQ-MC-009 — Every decision is resolved into the requirements or dismissed with a reason
A decision row SHALL be resolved, through the state tool, as either `requirement-revision` — naming the requirement
ids it added or changed in `requirements.md` and `spec-delta.md` and the `revision_history` entry, whose reason names
the mockup iteration and the decision ids — or `no-spec-impact` with a reason (for example, a spacing or grouping the
requirements do not specify); the state tool SHALL refuse a `requirement-revision` whose revision entry does not
exist or does not name the decision, and a `no-spec-impact` without a reason.

Traces to PRD: §6 S-2, O-2, AC-2 · Decision: D-40 · Builds on: the `revision_history` of `spec.json`, REQ-LD-014

**Scenario — success:** GIVEN `MD-03` WHEN `REQ-INV-011` ("the list offers a status filter") is added, the revision
entry names `MD-03`, and the row is resolved citing both THEN the row reads `requirement-revision REQ-INV-011`.
**Scenario — error:** GIVEN `MD-03` resolved as `requirement-revision REQ-INV-011` with no revision entry naming it
WHEN the resolution is recorded THEN the state tool refuses it with `no revision_history entry names MD-03`.

### 2.3 REQ-MC-010 — The mockup cannot be approved otherwise
WHILE the element check reports an error, a decision row is `unresolved`, a decision's revision entry is missing, or a
requirement cited by the element map no longer exists, the state tool SHALL refuse `approve mockup` and the approval
of any gate that covers the mockup, naming each cause.

Traces to PRD: §6 S-2, O-1, O-2, AC-1, AC-2 · Decision: D-40

**Scenario — success:** GIVEN a green element check and every decision resolved WHEN the owner approves the *what* gate
THEN the approval is recorded for requirements, mockup and design.
**Scenario — error:** GIVEN `MD-05` unresolved WHEN the owner answers the *what* gate with an approval THEN the state
tool refuses it with `mockup: MD-05 unresolved` and nothing is recorded.

### 2.4 REQ-MC-011 — Captured instructions reach the decision log
WHERE instruction capture is on (REQ-LD-001), an instruction row captured while the change is in the mockup phase and
classified `requirement-revision` SHALL be cited by a decision row; the state tool SHALL refuse the mockup approval
while such a row is cited by none.

Traces to PRD: §6 S-2, S-8, O-2 · Decision: D-40, D-38 · Builds on: REQ-LD-013, REQ-LD-016

**Scenario — success:** GIVEN instruction row `F-12` captured in the mockup phase and classified
`requirement-revision` WHEN `MD-04` cites `F-12` and is resolved THEN the mockup approval is not held by it.
**Scenario — error:** GIVEN `F-12` classified `requirement-revision` and no decision row citing it WHEN the mockup
approval is requested THEN the state tool refuses it naming `F-12`.

### 2.5 REQ-MC-012 — The approved mockup is frozen
WHEN the mockup is approved, and again WHEN the design is approved (design-graphic is the only phase that may change the
mockup files between the two, with the element check green), the state tool SHALL record the mockup hash (SHA-256 over
the mockup files and the element map); `validate` SHALL report `mockup changed after approval` when the files differ
from the last recorded hash, and `advance … impl` SHALL be refused until the mockup is re-opened through the iteration
skill and approved again.

Traces to PRD: §6 S-2, O-3, AC-3 · Decision: D-40

**Scenario — success:** GIVEN an approved mockup restyled by design-graphic and a design approval that re-recorded the
hash WHEN `advance … impl` runs THEN the hash matches and the phase advances.
**Scenario — error:** GIVEN the mockup edited after its approval WHEN `advance … impl` runs THEN the state tool refuses
it with `mockup changed after approval (re-open through karvey-iterate)`.

### 2.6 REQ-MC-013 — The gate that approves the mockup shows the revisions it carries
The summary of the gate that approves the mockup — the merged *what* gate or the granular mockup gate — SHALL list the
requirement revisions made during the mockup phase with their requirement and decision ids, and every decision
resolved `no-spec-impact` with its reason, and the approval SHALL
record them in its `ref`, so that one answer approves the mockup and the requirement revisions it caused; in the
granular mode no separate requirements re-approval SHALL be asked.

Traces to PRD: §6 S-2, S-8, O-2 · Decision: D-40, D-22 · Builds on: REQ-W2-034, REQ-W2-036

**Scenario — success:** GIVEN two requirement revisions from `MD-03` and `MD-05` WHEN the *what* gate is presented THEN
the summary lists `REQ-INV-011 (MD-03)` and `REQ-INV-004 changed (MD-05)` and the recorded approval names them.
**Scenario — error:** GIVEN a requirement revised in the mockup phase that the summary omits WHEN the summary is built
THEN the state tool reports the omission and the gate is not presented.

## Requirement 3: Implementation from the mockup (D-40 part 2)

### 3.1 REQ-MC-014 — The approved mockup is a mandatory input
WHERE a change is a UI change, the implementation skill SHALL read the approved mockup and its element map, verified
against the mockup hash, before any task that touches UI; `advance … impl` SHALL be refused while the mockup is not
approved or its hash does not match.

Traces to PRD: §6 S-3, O-3, AC-4 · Decision: D-40

**Scenario — success:** GIVEN an approved mockup with a matching hash WHEN impl starts THEN its context lists the
mockup files and the element map among its inputs.
**Scenario — error:** GIVEN a UI change whose mockup was never approved WHEN `advance … impl` runs THEN the state tool
refuses it with `mockup not approved`.

### 3.2 REQ-MC-015 — Tasks name the elements they build
In a UI change, the tasks skill SHALL list in each task that touches UI the element ids it builds, and SHALL precede
the first such task of each screen with a test task whose conformance presence check for those ids fails before the
implementation; the tasks approval SHALL be refused while an id of the element map is assigned to no task.

Traces to PRD: §6 S-3, O-3, AC-4 · Decision: D-40 · Builds on: REQ-W2-057

**Scenario — success:** GIVEN twelve element ids WHEN tasks are generated THEN each appears in at least one task and the
invoice-list screen starts with a presence test task.
**Scenario — error:** GIVEN `filter-status` in the element map and in no task WHEN tasks approval is requested THEN it
is refused naming `filter-status`.

### 3.3 REQ-MC-016 — Build from the mockup's structure and styles
WHEN the implementation skill builds a UI element, it SHALL take from the approved mockup the element's parent, its
order among siblings, its visible text and its states, and SHALL take its styles from the design-system tokens the
mockup references rather than from values it re-authors.

Traces to PRD: §6 S-3, O-3 · Decision: D-40 · Builds on: REQ-W3-035

**Scenario — success:** GIVEN the mockup's export button uses the token `color-action` WHEN impl builds it THEN the
built button references the same token and its text is the mockup's text.
**Scenario — error:** GIVEN the built button's text "Download" where the mockup says "Export" WHEN the task's presence
test runs THEN it fails with `text differs: export` (REQ-MC-054).

### 3.4 REQ-MC-055 — A difference the stack forces is declared when it is made
WHEN the stack cannot reproduce something the approved mockup shows, the implementation skill SHALL record a proposed
mockup deviation (REQ-MC-030) in the task that meets it, and the task's summary SHALL name it.

Traces to PRD: §6 S-3, S-5, O-3, O-5 · Decision: D-40

**Scenario — success:** GIVEN the stack's date picker cannot show the mockup's inline calendar WHEN impl builds the filter
THEN it records `DV-01` (`date-range`, proposed `accept`) in the same task, and the task's summary names it.
**Scenario — error:** GIVEN a task closed with a difference no deviation declares WHEN the conformance run later finds it
THEN the deviation it requires is recorded with origin `gate`, and the metrics count it as undeclared at impl.

### 3.5 REQ-MC-017 — The same element ids in the build
The built UI SHALL carry, on the element that realises each mockup element, the same element id in the form its
target defines (Requirement 7), in every build the conformance gate checks; a production build SHALL strip the ids
only WHERE the project's reviewed settings set `conformance.strip_in_production` to true (default false).

Traces to PRD: §6 S-3, O-3, AC-4 · Decision: D-40

**Scenario — success:** GIVEN the built invoice list in the development build WHEN the presence check queries `export`
THEN it finds exactly one element.
**Scenario — error:** GIVEN `strip_in_production: true` set only in the working copy WHEN the release build runs THEN the
ids are kept and the audit log records `conformance setting ignored (not reviewed)`.

### 3.6 REQ-MC-018 — No invented elements
The presence check SHALL report as `extra` every element id found in the build that the approved element map does not
contain; an `extra` id SHALL need a mockup deviation or its removal before the gate passes.

Traces to PRD: §6 S-3, S-4, O-3, O-5 · Decision: D-40

**Scenario — success:** GIVEN the build carries only ids of the element map WHEN the presence check runs THEN it reports
0 extra.
**Scenario — error:** GIVEN the build adds a `bulk-delete` button with an id not in the map WHEN the presence check runs
THEN it reports `extra: bulk-delete` and the gate stays closed until `DV-NN` covers it or it is removed.

## Requirement 4: The conformance gate (D-40 part 3)

### 4.1 REQ-MC-019 — A conformance plan from the element map
The tasks skill SHALL generate the conformance plan from the element map: one entry per mockup screen and per Level-4
state, each with its id, how to reach it in the mockup, how to reach it in the build (route or command, steps and the
fixture data it needs) and its viewports; every element id SHALL appear in at least one entry, and the plan SHALL name
fixture data only.

Traces to PRD: §6 S-4, O-4, AC-5 · Decision: D-40

**Scenario — success:** GIVEN an invoice list with an empty state and an export-error state WHEN the plan is generated
THEN it has three entries and each element id appears in at least one.
**Scenario — error:** GIVEN an element id reachable from no entry WHEN the plan is checked THEN it reports
`unplanned: <id>` and the tasks approval is refused.

### 4.2 REQ-MC-020 — Viewports
Each plan entry SHALL be captured at every viewport of the project's conformance settings — by default a desktop
viewport of 1280×800 and a phone viewport of 390×844 for web, and the declared device profiles for native targets —
unless the entry declares that its screen exists only at some of them.

Traces to PRD: §6 S-4, O-4 · Decision: D-40

**Scenario — success:** GIVEN no viewport setting WHEN the run captures the invoice list THEN it captures it at 1280×800
and at 390×844.
**Scenario — error:** GIVEN a viewport setting `1280x` (malformed) WHEN `validate` reads the settings THEN it reports
`conformance.viewports invalid` and the run does not start.

### 4.3 REQ-MC-021 — Every element is present (check a)
For each plan entry and viewport, the conformance run SHALL check in the running build that every element id the
mockup shows in that state is present and visible, and SHALL report each id as `present`, `missing` or `hidden`, plus
the `extra` ids of REQ-MC-018.

Traces to PRD: §6 S-4, O-3, O-4, AC-5 · Decision: D-40

**Scenario — success:** GIVEN the invoice list built with every id WHEN the run checks the entry at both viewports THEN
every id is `present`.
**Scenario — error:** GIVEN `filter-status` rendered but hidden at the phone viewport WHEN the run checks the entry
THEN it reports `hidden: filter-status @390x844`.

### 4.4 REQ-MC-022 — Same viewport, same state
The conformance run SHALL capture mockup and build for each entry and viewport with the same viewport size, pixel
ratio, colour scheme and locale, with animations and caret blinking disabled, after the entry's steps have been
applied to both, and with the elements the approved element map marks dynamic masked in both captures (a dynamic marker present only in
the build SHALL be ignored and reported as `unapproved dynamic marker`); each capture SHALL
record its entry, viewport, commit, time and SHA-256.

Traces to PRD: §6 S-4, O-4, AC-5 · Decision: D-40

**Scenario — success:** GIVEN the export-error entry WHEN the run captures it THEN both captures show the error state at
the same size and their records carry the same entry and viewport.
**Scenario — error:** GIVEN the build's steps fail to reach the export-error state WHEN the run captures the entry THEN
it reports `state not reached: export-error` for it and takes no build capture of the wrong state.

### 4.5 REQ-MC-023 — The difference is marked (check b)
For each capture pair, the conformance run SHALL produce a side-by-side image — mockup, build and a difference overlay
with each differing region outlined — and SHALL report per element id the difference of its box (position and size)
and, where the target exposes computed styles, the difference of its colour, font size and font weight against the
mockup.

Traces to PRD: §6 S-4, O-4, AC-5 · Decision: D-40

**Scenario — success:** GIVEN the build's export button 20 px lower than in the mockup WHEN the run compares the pair
THEN the overlay outlines the button and the report says `export: box Δy +20px`.
**Scenario — error:** GIVEN a capture pair whose images differ in pixel size WHEN the run compares them THEN it produces the
side-by-side without an overlay and marks the entry `unmeasured (size differs)` (REQ-MC-025).

### 4.6 REQ-MC-054 — Text and style differences are differences
For each element present in both captures of a pair, the conformance run SHALL compare its visible text (whitespace
normalised, approved dynamic elements excluded) and, where the target exposes computed styles, its colour, font size and
font weight with the mockup's, and SHALL mark the element `text differs` or `style differs` on any inequality, whatever
the pixel ratio of the pair.

Traces to PRD: §2, §6 S-4, O-4, O-5, AC-5 · Decision: D-40 (judge F-01, F-02)

**Scenario — success:** GIVEN the build's `export` with the mockup's text and tokens WHEN the run compares it THEN it is
neither `text differs` nor `style differs`.
**Scenario — error:** GIVEN the build's `export` reading "Download" and bold where the mockup reads "Export" in regular
weight, and a pair differing in 0.1% of its pixels WHEN the run compares it THEN it marks `export` `text differs` and
`style differs` and the entry needs a deviation.

### 4.7 REQ-MC-024 — Pixel difference against a threshold
WHERE both captures of a pair are images of the same pixel size, the conformance run SHALL compute the ratio of
differing pixels after masking, counting a pixel as differing when its colour distance exceeds `conformance.pixel_tolerance` (default 0.1 on a 0–1
scale), and SHALL mark the entry `over threshold` when the
ratio exceeds `conformance.pixel_threshold` (default 0.5%) or any element's box differs by more than
`conformance.box_tolerance_px` (default 4); the three values SHALL be read from the reviewed line of the project settings
only, never from the working copy or from the change.

Traces to PRD: §6 S-4, §9, O-4, AC-5 · Decision: D-40, D-01

**Scenario — success:** GIVEN a pair differing in 0.2% of its pixels and no box beyond 4 px WHEN the run compares it
THEN the entry is `within threshold`.
**Scenario — error:** GIVEN the agent raises `pixel_threshold` to 50% in the working copy WHEN the run compares a pair
differing in 12% THEN it uses the reviewed value, marks the entry `over threshold` and records
`conformance setting ignored (not reviewed)`.

### 4.8 REQ-MC-025 — Where no pixel difference is possible
WHERE a pair cannot be compared pixel by pixel (the target or the pair does not allow it), the conformance run SHALL
still produce the side-by-side image, SHALL mark the entry `unmeasured (<reason>)` and SHALL count it as a difference
that needs a mockup deviation (one deviation MAY cover several unmeasured entries of
the same screen, each listed with its side-by-side image).

Traces to PRD: §6 S-4, S-7, O-4, O-5, O-7 · Decision: D-40

**Scenario — success:** GIVEN a native screen whose mockup frame and simulator capture differ in pixel size WHEN the run
compares them THEN it marks the entry `unmeasured (size differs)` and the owner approves `DV-04` covering it.
**Scenario — error:** GIVEN an unmeasured entry with no deviation WHEN QA approval is requested THEN it is refused naming
the entry.

### 4.9 REQ-MC-026 — Captures run where the browse settings say
The conformance run SHALL take its captures where `browse.via` says: `local` in this session; `agent:<name>` by sending
the named agent a self-contained instruction — the development URL or command, the plan entries, the viewports and the
fixture user, never a secret value — and verifying what it returns (each capture's SHA-256, entry, viewport, commit,
and image size equal to the viewport times the pixel ratio); `none` by reporting `not evaluated`, which SHALL NOT count
as a pass and SHALL need a mockup deviation the owner approves (REQ-MC-030, 032).

Traces to PRD: §6 S-4, §9, O-4, AC-5 · Decision: D-40 · Builds on: REQ-W3-054

**Scenario — success:** GIVEN `browse.via: agent:ui-runner` WHEN the run delegates the captures and the returned
manifest matches every file THEN the report records the captures as `delegated, verified`.
**Scenario — error:** GIVEN a returned capture whose hash differs from its manifest line, or whose size does not match
its viewport WHEN the run verifies it THEN it rejects that capture as `unverified` and the entry has no result; GIVEN
`browse.via: none` THEN the report is `not evaluated` and the gate stays closed until the owner approves a deviation
covering it.

### 4.10 REQ-MC-027 — Never a production target
The conformance run SHALL refuse a build target that the project settings declare as production, and SHALL take build
captures only with the plan's fixture data.

Traces to PRD: §6 S-4, §7, §9 · Decision: D-40

**Scenario — success:** GIVEN the plan points at the development environment WHEN the run starts THEN it captures.
**Scenario — error:** GIVEN the plan's build URL equals the production URL of the project settings WHEN the run starts
THEN it refuses with `production target refused` and captures nothing.

### 4.11 REQ-MC-028 — Evidence lives in the change and is bound to its commit
The conformance run SHALL write the report, the element results and the side-by-side images under
`docs/spec/changes/<id>/conformance/`, recording the commit of the build and the mockup hash it checked; WHEN a later
commit of the change touches UI code (Conventions), or the last recorded mockup hash differs from the one the report
checked, the report SHALL be marked `stale` and SHALL NOT count at any gate.

Traces to PRD: §6 S-4, O-4, AC-7 · Decision: D-40 · Builds on: REQ-W2-061

**Scenario — success:** GIVEN a run at the change's last commit WHEN the release gate checks it THEN the report counts.
**Scenario — error:** GIVEN a UI commit after the run WHEN QA approval is requested THEN it is refused with
`conformance report stale (run at <commit>, UI changed at <commit>)`; GIVEN the mockup re-approved after a
`revise-mockup` deviation THEN the earlier report is `stale (mockup hash changed)`.

### 4.12 REQ-MC-029 — Where the captures are kept
The conformance settings SHALL accept `captures: commit` (default: images committed in the change) or `captures: local`
(images kept under the method's git-ignored state directory, the committed report holding only their SHA-256); in both
the report SHALL name every image and its hash.

Traces to PRD: §6 S-4, §9, O-4 · Decision: D-40

**Scenario — success:** GIVEN `captures: local` WHEN the run finishes THEN no image is staged and the report lists each
image's hash.
**Scenario — error:** GIVEN `captures: local` and a missing local image at the gate WHEN the gate checks the report THEN
it reports `capture missing: <name>` and asks for a re-run.

## Requirement 5: Mockup deviations and the owner's approval (D-40 part 3)

### 5.1 REQ-MC-030 — Every difference is a deviation entry
Every `missing`, `hidden` or `extra` id, every `text differs` or `style differs` element (REQ-MC-054), every
`unapproved dynamic marker`, every entry `over threshold`, `unmeasured`, `state not reached` or `not evaluated`, and
every difference the implementation declared (REQ-MC-055) SHALL be covered by a mockup deviation `DV-NN` with:
the element ids, the plan entries and viewports, the side-by-side images, what differs, why, the proposed resolution
(`fix-build`, `accept` or `revise-mockup`) and the status `pending`.

Traces to PRD: §6 S-5, O-5, AC-6 · Decision: D-40 · Builds on: the engineering-standards `deviations.md`

**Scenario — success:** GIVEN the run reports `export: box Δy +20px` WHEN the agent records `DV-02` (proposed
`fix-build`) THEN the report shows the difference covered by `DV-02`.
**Scenario — error:** GIVEN a reported difference covered by no entry WHEN the gate summary is built THEN it lists the
difference as `uncovered` and the gate stays closed.

### 5.2 REQ-MC-031 — How a deviation is resolved
A `fix-build` deviation SHALL be closed only by a later conformance run in which its difference is gone (status
`fixed`, written by the run); an `accept` deviation SHALL be closed only by the owner's approval (REQ-MC-032); a
`revise-mockup` deviation SHALL be routed through the iteration skill as a spec-revision that re-opens the mockup and
the requirements it affects, and SHALL be closed when the mockup is approved again and a new run passes.

Traces to PRD: §6 S-5, O-5 · Decision: D-40 · Builds on: the iteration loop

**Scenario — success:** GIVEN `DV-02` (`fix-build`) WHEN the button is fixed and the run shows no difference THEN the run
closes `DV-02` as `fixed`.
**Scenario — error:** GIVEN the agent sets `DV-02` to `fixed` by editing `deviations.md` while the difference remains
WHEN the next run or gate reads it THEN it reports the status as not written by the run and treats `DV-02` as `pending`.

### 5.3 REQ-MC-032 — Only the owner approves a deviation, through the hook
An `accept` deviation SHALL count as approved only when the hook recognised the deviation confirm phrase
(`approve deviation DV-NN`, a list of at most 10 ids and no ranges, in the vocabulary's shipped languages) in the owner's own prompt
and wrote a one-use marker naming the deviation ids and the SHA-256 of each entry's text; the state tool SHALL record
the approval from that marker; an approval without its marker, or whose entry text changed after the marker, SHALL be
reported as tampered and SHALL NOT count; a message from any agent SHALL never count; a phrase naming more than 10 ids SHALL write no
marker and SHALL tell the owner why.

Traces to PRD: §6 S-5, §9, O-5, AC-6 · Decision: D-40, D-01 · Builds on: REQ-W1-017, REQ-LD-063

**Scenario — success:** GIVEN `DV-01` pending WHEN the owner writes "approve deviation DV-01" THEN the hook writes the
marker and the state tool records `DV-01 accepted (owner, <time>)`.
**Scenario — error:** GIVEN the agent writes `approved` on `DV-01` in `deviations.md` WHEN the state tool validates the
change THEN it reports `DV-01 approval tampered (no marker)` and `DV-01` stays pending; GIVEN `DV-01`'s text edited
after its approval THEN the approval is void and `DV-01` is pending again.

### 5.4 REQ-MC-033 — No QA approval, release or deploy otherwise
WHILE, in a UI change, the conformance report is missing or `stale`, a difference (including `not evaluated`) is
uncovered, or a deviation is `pending` or tampered, the state tool SHALL refuse `approve qa`, the release gate and the
production approval, and the deploy skill SHALL refuse to start, naming each.

Traces to PRD: §6 S-5, O-5, AC-6, AC-7 · Decision: D-40 · Builds on: REQ-W2-034, REQ-W2-039

**Scenario — success:** GIVEN a fresh report whose differences are all `fixed` or `accepted` WHEN the release gate is
approved THEN QA and production approvals are recorded.
**Scenario — error:** GIVEN `DV-03` pending WHEN the owner answers the release gate with an approval THEN the state tool
refuses it with `conformance: DV-03 pending` and records nothing.

### 5.5 REQ-MC-034 — The owner sees the differences at the gate
The summary of the gate that approves QA (the merged release gate or the granular qa gate) SHALL show the number of
plan entries per result (`pass`, `fixed`, `accepted`, `pending`, `over threshold`, `unmeasured`, `state not reached`,
`not evaluated`, `not applicable`), each pending deviation with the path of
its side-by-side image, and the report's path and commit.

Traces to PRD: §6 S-5, O-5 · Decision: D-40 · Builds on: REQ-W2-027

**Scenario — success:** GIVEN 9 entries passing and 1 accepted WHEN the release gate is presented THEN the summary reads
`conformance: 9 pass · 1 accepted (DV-01) · report @<commit>`.
**Scenario — error:** GIVEN a pending deviation whose side-by-side image is missing WHEN the summary is built THEN it
reports `DV-03: capture missing` instead of omitting the image.

### 5.6 REQ-MC-035 — QA's visual audit compares with the approved mockup
QA's visual audit SHALL cite the conformance report as its evidence of conformance with the approved mockup and SHALL
keep the audit against the design specification and the platform guide for what the mockup does not fix
(accessibility, focus, platform conventions); a conformance statement without the report SHALL read `not evaluated`,
and the fiscal judge's rubric SHALL list every conformance claim of the review that does not cite the report.

Traces to PRD: §6 S-5, S-8, O-4, O-5 · Decision: D-40 · Builds on: REQ-W2-032, REQ-W2-063

**Scenario — success:** GIVEN a fresh report WHEN QA writes its review THEN the visual dimension cites the report's path
and commit.
**Scenario — error:** GIVEN a review that says "the UI matches the mockup" with no report WHEN the fiscal judge runs THEN
it lists that claim as without evidence.

## Requirement 7: Targets

### 7.1 REQ-MC-038 — Web
WHERE the target is web, the element id SHALL be the `data-mk` attribute of the DOM element; presence SHALL be checked
in the rendered document, including visibility; a capture SHALL be a browser screenshot of the viewport; the pixel
difference of REQ-MC-024 SHALL apply.

Traces to PRD: §6 S-7, O-7 · Decision: D-40

**Scenario — success:** GIVEN a web build WHEN the run checks the invoice list THEN presence comes from the rendered
document and the pair has a pixel ratio.
**Scenario — error:** GIVEN an id that exists only in a template file and is never rendered WHEN the run checks the entry
THEN it reports `missing`, not `present`.

### 7.2 REQ-MC-039 — Mobile and desktop
WHERE the target is a native mobile or desktop application, the mockup SHALL be rendered in frames of the declared
device profile; the element id SHALL be the platform's accessibility or test identifier set to the same value;
presence SHALL be read from the running application's accessibility tree on a simulator, emulator or desktop session;
a capture SHALL be the screen of that session at the device profile; the pixel difference SHALL apply only when both
captures have the same pixel size (REQ-MC-025 otherwise); WHERE the runtime exposes no accessibility tree, presence
SHALL be `not evaluated` for that entry and SHALL need a deviation.

Traces to PRD: §6 S-7, O-7 · Decision: D-40 · Builds on: the target rule (mobile runtime)

**Scenario — success:** GIVEN a mobile build whose export button's accessibility identifier is `export` WHEN the run
reads the tree THEN `export` is `present`.
**Scenario — error:** GIVEN a desktop toolkit without an accessibility tree WHEN the run checks an entry THEN presence is
`not evaluated` and the gate asks for a deviation covering it.

### 7.3 REQ-MC-040 — Command line
WHERE the target is a command-line interface, the mockup SHALL be a transcript in which each output block that a
requirement names carries a marker line `[mk:<id>]` and an anchor (a literal line or a pattern); presence SHALL be each
anchor found in the real output of the same command with the same inputs; a capture SHALL be that real transcript at
the declared terminal width (default 80 columns); the difference SHALL be a normalised text difference (trailing spaces
and colour codes removed, declared dynamic patterns masked), and no pixel difference SHALL apply.

Traces to PRD: §6 S-7, O-7, AC-9 · Decision: D-40

**Scenario — success:** GIVEN a mockup transcript with `[mk:summary-table]` anchored on `Total invoices:` WHEN the real
command prints that line THEN `summary-table` is `present` and the text difference is empty after masking.
**Scenario — error:** GIVEN the real command prints `Invoices total:` instead WHEN the run compares THEN it reports
`missing: summary-table` and the text difference.

### 7.4 REQ-MC-041 — Every other target is out of scope by name
WHERE a UI change's target is none of web, mobile, desktop or command line (for example an API, embedded firmware, a
game engine, a data pipeline or a library), the conformance gate SHALL report `not applicable: target <t>` in the gate
summary and SHALL neither refuse nor record a pass; the report SHALL be written with that result, which satisfies
REQ-MC-033 and fills the matrix's conformance cells with `n/a (target <t>)` for REQ-MC-037; the existing visual audit
SHALL apply; a project with several
targets SHALL apply the gate to each defined target it builds.

Traces to PRD: §6 S-7, §7, O-7, AC-9 · Decision: D-40

**Scenario — success:** GIVEN a change with targets `web` and `api` WHEN the gate runs THEN it checks web and reports
`not applicable: target api`; GIVEN a UI change whose only target is `api` THEN the release gate is not refused on
conformance and the matrix shows `n/a (target api)`.
**Scenario — error:** GIVEN a target missing from the project settings WHEN the gate runs THEN it reports
`target undeclared` and refuses until the target is declared.

## Explicit exclusions
- Changes without a mockup (lanes that skip it, `patch`, `hotfix`) are not checked against a mockup; they keep today's
  visual audit (plus the sheet warning of REQ-MC-046).
- Retroactive conformance of UI shipped, or mockups approved, before 4.3.0 (REQ-MC-048 makes it advisory).
- API/backend, embedded, game, data and library targets (REQ-MC-041).
- Pixel-exact equality, and any automatic "fix" of a difference by the gate.
- Capturing a production environment or production data.
- Requiring a specific browser automation or image-comparison product.
- Anything under the user's home directory or the owner's global configuration.
- Behaviour that does not change: the engineering-standards deviations of `deviations.md` and their approval at
  design time; the finding types of the iteration loop; the design judge's closed inputs; the approval vocabulary's
  approval, negation and production lists.
