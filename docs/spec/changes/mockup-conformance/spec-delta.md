# Spec Delta: mockup-conformance

Against the living spec `docs/spec/specs/method/spec.md` (capability `method`). Baseline: the blocks already there
**plus** the REQ-W1-* blocks of `wave1-hardening`, the REQ-W2-* blocks of `wave2-structural`, the REQ-UP-* blocks of
`project-upgrade`, the REQ-W3-* blocks of `wave3-optimization` and the REQ-LD-* blocks of `living-docs`, treated as
already merged (those changes ship first). Merge order: wave1, wave2, project-upgrade, wave3, living-docs, then this
delta. Single spec-delta path: this file, at the change root. Scenarios for every block are in `requirements.md`; the
living spec keeps the compact form.

Summary: **ADDED 51** (REQ-MC-001..035, 037..045, 047..051, 054, 055) · **MODIFIED 2** (REQ-W2-060 through REQ-MC-036,
REQ-LD-022 through REQ-MC-046 — those two are merged only as amendments, never added twice) · **REMOVED 0** ·
**change-scoped 2** (REQ-MC-052, 053 — bind this change only and are not merged; last section).

Why only two MODIFIED: the living spec states no requirement about the mockup's content, implementation inputs or
QA's visual audit (those live only in the skills), so REQ-MC-001..035 add behaviour without changing a living text.
REQ-MC-013 and 043 place new checks in the gates of REQ-W2-034 and 039 without changing which phases each gate
covers; REQ-MC-026 uses `browse.via` as REQ-W3-054 defines it; REQ-MC-032 reuses the confirm-phrase pattern of
REQ-LD-063 with a new phrase; REQ-MC-047 adds steps to the catalogue whose shape REQ-UP-008 defines; REQ-MC-049 adds
rows to the registry whose rule REQ-W3-061 and REQ-LD-053 state for their own checks; REQ-MC-037 adds a release
refusal next to the coverage gate of REQ-W2-062 without changing it; REQ-MC-007 adds a refusal to the design approval
without changing the design judge of REQ-W3-039 (judge F-29: these add refusal conditions around gates whose living
text lists what the gate covers, not every condition that refuses it — the same reading `living-docs` applied). REQ-W2-060 (what the matrix maps) and REQ-LD-022 (the sections of the
frontend-module template) change their text, so they are MODIFIED.

## ADDED Requirements

### ADDED by `mockup-conformance` (4.3.0)

Traced to `docs/spec/changes/mockup-conformance/prd.md` and decision D-40.

### Element ids in the mockup (D-40 part 1)
- **REQ-MC-001** — Required elements carry an element id. WHERE a change is a UI change, the mockup skill SHALL give an element id to every mockup element of these kinds: screen or view; overlay (dialog, drawer, menu, toast); region (a named area of a screen, such as a filter bar, a table or a form section); control (button, link, input, select, toggle, tab); message (validation, error, empty, success); and the container of each Level-4 state. A decorative element or a layout wrapper that no requirement names SHALL NOT need one. *(Traces: PRD §6 S-1, O-1, AC-1 · Decision: D-40)*
- **REQ-MC-002** — Id format and uniqueness. An element id SHALL match `[a-z0-9]+(-[a-z0-9]+)*`, be at most 48 characters long, contain no run of 6 or more digits and no match of the method's secret patterns, and be unique within the change's mockup, except that the instances of a repeated element (list rows, cards) SHALL share one id and each carry the repeat marker. *(Traces: PRD §6 S-1, §9, O-1, AC-1 · Decision: D-40)*
- **REQ-MC-003** — Each element names the requirements it covers. Every element with an element id SHALL carry the requirement attribute listing at least one requirement id of the change or of the living spec, or the value `gap`; the element check SHALL report an unknown requirement id as an error and an element marked `gap` as a spec-gap to route through the iteration skill (a requirement added or the element removed). *(Traces: PRD §6 S-1, O-1, AC-1 · Decision: D-40 · Builds on: the mockup skill's spec↔mockup validation)*
- **REQ-MC-004** — Every UI requirement is covered; every cited one is UI. In a UI change, every requirement of the change SHALL declare its surface (`Surface: ui` or `Surface: none`) on its trace line; the element check SHALL report every `ui` requirement of the change that no element cites and every element that cites a `none` requirement of the change; a living-spec requirement cited by an element SHALL be treated as `ui` for that element and SHALL NOT count in the change's coverage. *(Traces: PRD §6 S-1, O-1, AC-1 · Decision: D-40)*
- **REQ-MC-005** — The element check is deterministic and writes the element map. The element check SHALL read the change's mockup files, SHALL write the element map — for each id: its kind, the screen and state it belongs to, its parent id, its order among siblings, its visible text, its requirement ids and whether it repeats — and SHALL report every violation of REQ-MC-001 to REQ-MC-004 and REQ-MC-006 with the element's path; for the same input it SHALL produce byte-identical output and SHALL exit non-zero while any error remains. The mockup skill SHALL run it on every generated iteration and before presenting the mockup. *(Traces: PRD §6 S-1, O-1, AC-1 · Decision: D-40)*
- **REQ-MC-006** — Ids are stable across iterations. Once an element id has appeared in a generated iteration of the change's mockup, it SHALL keep denoting an element of the same kind on the same screen; the element check SHALL compare the new iteration with the previous element map and SHALL list removed ids, SHALL accept a renamed id only when the element map records it as `old → new`, and SHALL refuse an id that was removed in an earlier iteration and now denotes an element of another kind or screen. *(Traces: PRD §6 S-1, O-1 · Decision: D-40)*
- **REQ-MC-007** — Design-graphic keeps the ids. WHEN design-graphic updates the mockup with the visual system, it SHALL keep every element id, requirement attribute, repeat marker and dynamic marker; the element check SHALL run after it, and the design approval SHALL be refused while it reports a lost or changed id without a recorded rename. *(Traces: PRD §6 S-1, S-8, O-1 · Decision: D-40 · Builds on: REQ-W3-036)*

### Decisions written back (D-40 part 1)
- **REQ-MC-008** — Every iteration decision is logged. WHEN the owner gives feedback on a mockup iteration, the mockup skill SHALL record through the state tool, in the decision log, one row per decision it applies — anything that changes a behaviour, a field, a state, a validation, a text, an order or what is visible — with the iteration number, the owner's words (a short quote, or the instruction row `F-NN` when instruction capture is on), the element ids affected and the status `unresolved`; a change the agent makes on its own initiative (fixing a spec-gap, a restyle by design-graphic) SHALL be recorded the same way with origin `agent`. The element check SHALL report every element added or removed, and every element whose text or requirement attribute changed, between two iterations that no decision row cites. *(Traces: PRD §6 S-2, O-2, AC-2 · Decision: D-40)*
- **REQ-MC-009** — Every decision is resolved into the requirements or dismissed with a reason. A decision row SHALL be resolved, through the state tool, as either `requirement-revision` — naming the requirement ids it added or changed in `requirements.md` and `spec-delta.md` and the `revision_history` entry, whose reason names the mockup iteration and the decision ids — or `no-spec-impact` with a reason (for example, a spacing or grouping the requirements do not specify); the state tool SHALL refuse a `requirement-revision` whose revision entry does not exist or does not name the decision, and a `no-spec-impact` without a reason. *(Traces: PRD §6 S-2, O-2, AC-2 · Decision: D-40 · Builds on: the `revision_history` of `spec.json`, REQ-LD-014)*
- **REQ-MC-010** — The mockup cannot be approved otherwise. WHILE the element check reports an error, a decision row is `unresolved`, a decision's revision entry is missing, or a requirement cited by the element map no longer exists, the state tool SHALL refuse `approve mockup` and the approval of any gate that covers the mockup, naming each cause. *(Traces: PRD §6 S-2, O-1, O-2, AC-1, AC-2 · Decision: D-40)*
- **REQ-MC-011** — Captured instructions reach the decision log. WHERE instruction capture is on (REQ-LD-001), an instruction row captured while the change is in the mockup phase and classified `requirement-revision` SHALL be cited by a decision row; the state tool SHALL refuse the mockup approval while such a row is cited by none. *(Traces: PRD §6 S-2, S-8, O-2 · Decision: D-40, D-38 · Builds on: REQ-LD-013, REQ-LD-016)*
- **REQ-MC-012** — The approved mockup is frozen. WHEN the mockup is approved, and again WHEN the design is approved (design-graphic is the only phase that may change the mockup files between the two, with the element check green), the state tool SHALL record the mockup hash (SHA-256 over the mockup files and the element map); `validate` SHALL report `mockup changed after approval` when the files differ from the last recorded hash, and `advance … impl` SHALL be refused until the mockup is re-opened through the iteration skill and approved again. *(Traces: PRD §6 S-2, O-3, AC-3 · Decision: D-40)*
- **REQ-MC-013** — The gate that approves the mockup shows the revisions it carries. The summary of the gate that approves the mockup — the merged *what* gate or the granular mockup gate — SHALL list the requirement revisions made during the mockup phase with their requirement and decision ids, and every decision resolved `no-spec-impact` with its reason, and the approval SHALL record them in its `ref`, so that one answer approves the mockup and the requirement revisions it caused; in the granular mode no separate requirements re-approval SHALL be asked. *(Traces: PRD §6 S-2, S-8, O-2 · Decision: D-40, D-22 · Builds on: REQ-W2-034, REQ-W2-036)*

### Implementation from the mockup (D-40 part 2)
- **REQ-MC-014** — The approved mockup is a mandatory input. WHERE a change is a UI change, the implementation skill SHALL read the approved mockup and its element map, verified against the mockup hash, before any task that touches UI; `advance … impl` SHALL be refused while the mockup is not approved or its hash does not match. *(Traces: PRD §6 S-3, O-3, AC-4 · Decision: D-40)*
- **REQ-MC-015** — Tasks name the elements they build. In a UI change, the tasks skill SHALL list in each task that touches UI the element ids it builds, and SHALL precede the first such task of each screen with a test task whose conformance presence check for those ids fails before the implementation; the tasks approval SHALL be refused while an id of the element map is assigned to no task. *(Traces: PRD §6 S-3, O-3, AC-4 · Decision: D-40 · Builds on: REQ-W2-057)*
- **REQ-MC-016** — Build from the mockup's structure and styles. WHEN the implementation skill builds a UI element, it SHALL take from the approved mockup the element's parent, its order among siblings, its visible text and its states, and SHALL take its styles from the design-system tokens the mockup references rather than from values it re-authors. *(Traces: PRD §6 S-3, O-3 · Decision: D-40 · Builds on: REQ-W3-035)*
- **REQ-MC-055** — A difference the stack forces is declared when it is made. WHEN the stack cannot reproduce something the approved mockup shows, the implementation skill SHALL record a proposed mockup deviation (REQ-MC-030) in the task that meets it, and the task's summary SHALL name it. *(Traces: PRD §6 S-3, S-5, O-3, O-5 · Decision: D-40)*
- **REQ-MC-017** — The same element ids in the build. The built UI SHALL carry, on the element that realises each mockup element, the same element id in the form its target defines (Requirement 7), in every build the conformance gate checks; a production build SHALL strip the ids only WHERE the project's reviewed settings set `conformance.strip_in_production` to true (default false). *(Traces: PRD §6 S-3, O-3, AC-4 · Decision: D-40)*
- **REQ-MC-018** — No invented elements. The presence check SHALL report as `extra` every element id found in the build that the approved element map does not contain; an `extra` id SHALL need a mockup deviation or its removal before the gate passes. *(Traces: PRD §6 S-3, S-4, O-3, O-5 · Decision: D-40)*

### The conformance gate (D-40 part 3)
- **REQ-MC-019** — A conformance plan from the element map. The tasks skill SHALL generate the conformance plan from the element map: one entry per mockup screen and per Level-4 state, each with its id, how to reach it in the mockup, how to reach it in the build (route or command, steps and the fixture data it needs) and its viewports; every element id SHALL appear in at least one entry, and the plan SHALL name fixture data only. *(Traces: PRD §6 S-4, O-4, AC-5 · Decision: D-40)*
- **REQ-MC-020** — Viewports. Each plan entry SHALL be captured at every viewport of the project's conformance settings — by default a desktop viewport of 1280×800 and a phone viewport of 390×844 for web, and the declared device profiles for native targets — unless the entry declares that its screen exists only at some of them. *(Traces: PRD §6 S-4, O-4 · Decision: D-40)*
- **REQ-MC-021** — Every element is present (check a). For each plan entry and viewport, the conformance run SHALL check in the running build that every element id the mockup shows in that state is present and visible, and SHALL report each id as `present`, `missing` or `hidden`, plus the `extra` ids of REQ-MC-018. *(Traces: PRD §6 S-4, O-3, O-4, AC-5 · Decision: D-40)*
- **REQ-MC-022** — Same viewport, same state. The conformance run SHALL capture mockup and build for each entry and viewport with the same viewport size, pixel ratio, colour scheme and locale, with animations and caret blinking disabled, after the entry's steps have been applied to both, and with the elements the approved element map marks dynamic masked in both captures (a dynamic marker present only in the build SHALL be ignored and reported as `unapproved dynamic marker`); each capture SHALL record its entry, viewport, commit, time and SHA-256. *(Traces: PRD §6 S-4, O-4, AC-5 · Decision: D-40)*
- **REQ-MC-023** — The difference is marked (check b). For each capture pair, the conformance run SHALL produce a side-by-side image — mockup, build and a difference overlay with each differing region outlined — and SHALL report per element id the difference of its box (position and size) and, where the target exposes computed styles, the difference of its colour, font size and font weight against the mockup. *(Traces: PRD §6 S-4, O-4, AC-5 · Decision: D-40)*
- **REQ-MC-054** — Text and style differences are differences. For each element present in both captures of a pair, the conformance run SHALL compare its visible text (whitespace normalised, approved dynamic elements excluded) and, where the target exposes computed styles, its colour, font size and font weight with the mockup's, and SHALL mark the element `text differs` or `style differs` on any inequality, whatever the pixel ratio of the pair. *(Traces: PRD §2, §6 S-4, O-4, O-5, AC-5 · Decision: D-40 (judge F-01, F-02))*
- **REQ-MC-024** — Pixel difference against a threshold. WHERE both captures of a pair are images of the same pixel size, the conformance run SHALL compute the ratio of differing pixels after masking, counting a pixel as differing when its colour distance exceeds `conformance.pixel_tolerance` (default 0.1 on a 0–1 scale), and SHALL mark the entry `over threshold` when the ratio exceeds `conformance.pixel_threshold` (default 0.5%) or any element's box differs by more than `conformance.box_tolerance_px` (default 4); the three values SHALL be read from the reviewed line of the project settings only, never from the working copy or from the change. *(Traces: PRD §6 S-4, §9, O-4, AC-5 · Decision: D-40, D-01)*
- **REQ-MC-025** — Where no pixel difference is possible. WHERE a pair cannot be compared pixel by pixel (the target or the pair does not allow it), the conformance run SHALL still produce the side-by-side image, SHALL mark the entry `unmeasured (<reason>)` and SHALL count it as a difference that needs a mockup deviation (one deviation MAY cover several unmeasured entries of the same screen, each listed with its side-by-side image). *(Traces: PRD §6 S-4, S-7, O-4, O-5, O-7 · Decision: D-40)*
- **REQ-MC-026** — Captures run where the browse settings say. The conformance run SHALL take its captures where `browse.via` says: `local` in this session; `agent:<name>` by sending the named agent a self-contained instruction — the development URL or command, the plan entries, the viewports and the fixture user, never a secret value — and verifying what it returns (each capture's SHA-256, entry, viewport, commit, and image size equal to the viewport times the pixel ratio); `none` by reporting `not evaluated`, which SHALL NOT count as a pass and SHALL need a mockup deviation the owner approves (REQ-MC-030, 032). *(Traces: PRD §6 S-4, §9, O-4, AC-5 · Decision: D-40 · Builds on: REQ-W3-054)*
- **REQ-MC-027** — Never a production target. The conformance run SHALL refuse a build target that the project settings declare as production, and SHALL take build captures only with the plan's fixture data. *(Traces: PRD §6 S-4, §7, §9 · Decision: D-40)*
- **REQ-MC-028** — Evidence lives in the change and is bound to its commit. The conformance run SHALL write the report, the element results and the side-by-side images under `docs/spec/changes/<id>/conformance/`, recording the commit of the build and the mockup hash it checked; WHEN a later commit of the change touches UI code (Conventions), or the last recorded mockup hash differs from the one the report checked, the report SHALL be marked `stale` and SHALL NOT count at any gate. *(Traces: PRD §6 S-4, O-4, AC-7 · Decision: D-40 · Builds on: REQ-W2-061)*
- **REQ-MC-029** — Where the captures are kept. The conformance settings SHALL accept `captures: commit` (default: images committed in the change) or `captures: local` (images kept under the method's git-ignored state directory, the committed report holding only their SHA-256); in both the report SHALL name every image and its hash. *(Traces: PRD §6 S-4, §9, O-4 · Decision: D-40)*

### Mockup deviations and the owner's approval (D-40 part 3)
- **REQ-MC-030** — Every difference is a deviation entry. Every `missing`, `hidden` or `extra` id, every `text differs` or `style differs` element (REQ-MC-054), every `unapproved dynamic marker`, every entry `over threshold`, `unmeasured`, `state not reached` or `not evaluated`, and every difference the implementation declared (REQ-MC-055) SHALL be covered by a mockup deviation `DV-NN` with: the element ids, the plan entries and viewports, the side-by-side images, what differs, why, the proposed resolution (`fix-build`, `accept` or `revise-mockup`) and the status `pending`. *(Traces: PRD §6 S-5, O-5, AC-6 · Decision: D-40 · Builds on: the engineering-standards `deviations.md`)*
- **REQ-MC-031** — How a deviation is resolved. A `fix-build` deviation SHALL be closed only by a later conformance run in which its difference is gone (status `fixed`, written by the run); an `accept` deviation SHALL be closed only by the owner's approval (REQ-MC-032); a `revise-mockup` deviation SHALL be routed through the iteration skill as a spec-revision that re-opens the mockup and the requirements it affects, and SHALL be closed when the mockup is approved again and a new run passes. *(Traces: PRD §6 S-5, O-5 · Decision: D-40 · Builds on: the iteration loop)*
- **REQ-MC-032** — Only the owner approves a deviation, through the hook. An `accept` deviation SHALL count as approved only when the hook recognised the deviation confirm phrase (`approve deviation DV-NN`, a list of at most 10 ids and no ranges, in the vocabulary's shipped languages) in the owner's own prompt and wrote a one-use marker naming the deviation ids and the SHA-256 of each entry's text; the state tool SHALL record the approval from that marker; an approval without its marker, or whose entry text changed after the marker, SHALL be reported as tampered and SHALL NOT count; a message from any agent SHALL never count; a phrase naming more than 10 ids SHALL write no marker and SHALL tell the owner why. *(Traces: PRD §6 S-5, §9, O-5, AC-6 · Decision: D-40, D-01 · Builds on: REQ-W1-017, REQ-LD-063)*
- **REQ-MC-033** — No QA approval, release or deploy otherwise. WHILE, in a UI change, the conformance report is missing or `stale`, a difference (including `not evaluated`) is uncovered, or a deviation is `pending` or tampered, the state tool SHALL refuse `approve qa`, the release gate and the production approval, and the deploy skill SHALL refuse to start, naming each. *(Traces: PRD §6 S-5, O-5, AC-6, AC-7 · Decision: D-40 · Builds on: REQ-W2-034, REQ-W2-039)*
- **REQ-MC-034** — The owner sees the differences at the gate. The summary of the gate that approves QA (the merged release gate or the granular qa gate) SHALL show the number of plan entries per result (`pass`, `fixed`, `accepted`, `pending`, `over threshold`, `unmeasured`, `state not reached`, `not evaluated`, `not applicable`), each pending deviation with the path of its side-by-side image, and the report's path and commit. *(Traces: PRD §6 S-5, O-5 · Decision: D-40 · Builds on: REQ-W2-027)*
- **REQ-MC-035** — QA's visual audit compares with the approved mockup. QA's visual audit SHALL cite the conformance report as its evidence of conformance with the approved mockup and SHALL keep the audit against the design specification and the platform guide for what the mockup does not fix (accessibility, focus, platform conventions); a conformance statement without the report SHALL read `not evaluated`, and the fiscal judge's rubric SHALL list every conformance claim of the review that does not cite the report. *(Traces: PRD §6 S-5, S-8, O-4, O-5 · Decision: D-40 · Builds on: REQ-W2-032, REQ-W2-063)*

### Traceability before release (D-40 part 4)
- **REQ-MC-037** — Complete before the release gate opens. WHILE a `ui` requirement of a UI change has no element id, no green test, or an element without a conformance result that is `pass`, `fixed`, `accepted` or `n/a (target <t>)` (REQ-MC-041), the state tool SHALL refuse the release gate, naming the requirement and the empty cell. *(Traces: PRD §6 S-6, O-6, AC-8 · Decision: D-40 · Builds on: REQ-W2-062)*

### Targets
- **REQ-MC-038** — Web. WHERE the target is web, the element id SHALL be the `data-mk` attribute of the DOM element; presence SHALL be checked in the rendered document, including visibility; a capture SHALL be a browser screenshot of the viewport; the pixel difference of REQ-MC-024 SHALL apply. *(Traces: PRD §6 S-7, O-7 · Decision: D-40)*
- **REQ-MC-039** — Mobile and desktop. WHERE the target is a native mobile or desktop application, the mockup SHALL be rendered in frames of the declared device profile; the element id SHALL be the platform's accessibility or test identifier set to the same value; presence SHALL be read from the running application's accessibility tree on a simulator, emulator or desktop session; a capture SHALL be the screen of that session at the device profile; the pixel difference SHALL apply only when both captures have the same pixel size (REQ-MC-025 otherwise); WHERE the runtime exposes no accessibility tree, presence SHALL be `not evaluated` for that entry and SHALL need a deviation. *(Traces: PRD §6 S-7, O-7 · Decision: D-40 · Builds on: the target rule (mobile runtime))*
- **REQ-MC-040** — Command line. WHERE the target is a command-line interface, the mockup SHALL be a transcript in which each output block that a requirement names carries a marker line `[mk:<id>]` and an anchor (a literal line or a pattern); presence SHALL be each anchor found in the real output of the same command with the same inputs; a capture SHALL be that real transcript at the declared terminal width (default 80 columns); the difference SHALL be a normalised text difference (trailing spaces and colour codes removed, declared dynamic patterns masked), and no pixel difference SHALL apply. *(Traces: PRD §6 S-7, O-7, AC-9 · Decision: D-40)*
- **REQ-MC-041** — Every other target is out of scope by name. WHERE a UI change's target is none of web, mobile, desktop or command line (for example an API, embedded firmware, a game engine, a data pipeline or a library), the conformance gate SHALL report `not applicable: target <t>` in the gate summary and SHALL neither refuse nor record a pass; the report SHALL be written with that result, which satisfies REQ-MC-033 and fills the matrix's conformance cells with `n/a (target <t>)` for REQ-MC-037; the existing visual audit SHALL apply; a project with several targets SHALL apply the gate to each defined target it builds. *(Traces: PRD §6 S-7, §7, O-7, AC-9 · Decision: D-40)*

### Integration with the method
- **REQ-MC-042** — Lanes. Every check of this change except the sheet element check of REQ-MC-046 SHALL apply only to UI changes; a lane that skips the mockup SHALL see none of them but that one; WHEN a change's lane is raised to one that runs the mockup, the checks SHALL become pending with the phases the raise makes pending. *(Traces: PRD §6 S-8, §7 · Decision: D-40 · Builds on: REQ-W2-011, REQ-W2-015, REQ-W2-016)*
- **REQ-MC-043** — Which gate holds which check. The element check, decision resolution and captured-instruction link SHALL hold the gate that approves the mockup (the *what* gate when merged); the element assignment and the conformance plan SHALL hold the gate that approves tasks (the *how* gate); the conformance gate, the deviations and the matrix SHALL hold the gate that approves QA and production (the *release* gate); in granular mode each holds its own phase's approval. *(Traces: PRD §6 S-8 · Decision: D-40, D-22 · Builds on: REQ-W2-034, REQ-W2-039)*
- **REQ-MC-044** — The design system carries through. In a UI change that runs design-graphic, the approved mockup SHALL express its styles through the names of the project's design-system tokens, the build SHALL use the same token names, and the conformance run SHALL report a token the build uses that the design system does not declare; the style differences of REQ-MC-023 SHALL be computed on the values those tokens resolve to. *(Traces: PRD §6 S-8, O-4 · Decision: D-40 · Builds on: REQ-W3-035, REQ-W3-036, REQ-W3-038)*
- **REQ-MC-045** — Loaded only by the phases that act on it. The new rule of this change SHALL be named only in the load lists of the mockup, design-graphic, tasks, impl, test, qa, deploy and archive skills; the size tool SHALL store a snapshot of the implementation's base (with `living-docs`' implementation merged) before the first implementation commit and, WHEN this change's implementation is complete, SHALL report every phase's closure against it; the test phase SHALL fail if any phase's closure grows by more than 10%; the plugin linter SHALL fail when a skill outside that list names the rule. *(Traces: PRD §6 S-8, O-9, AC-11 · Decision: D-40 · Builds on: REQ-W3-001, REQ-W3-004, REQ-W3-011)*
- **REQ-MC-047** — Upgrade steps for existing projects. The project-upgrade step catalogue SHALL contain three steps, each with the seven declared fields: `MC-1` adds the conformance settings with their defaults (dry-run: yes; needs a human: no; risk low); `MC-2`, for each UI change in flight whose mockup is not approved yet, proposes element ids and requirement attributes for its mockup as a draft the owner reviews and approves with the mockup (dry-run: yes; needs a human: yes; risk medium); `MC-3` checks the capture capability the browse settings name and reports it (check only, no fix; risk low); each SHALL be idempotent and applied on the upgrade branch only. *(Traces: PRD §6 S-8, O-8, AC-10 · Decision: D-40, D-20 · Builds on: REQ-UP-008, REQ-UP-011..014)*
- **REQ-MC-048** — Changes already past their mockup. WHERE a UI change's mockup was approved before the project adopted 4.3.0, every check of this change SHALL run in warn mode for it, and its gate summaries SHALL say `mockup approved before 4.3 — conformance advisory`. *(Traces: PRD §7, §9, O-8 · Decision: D-40, D-24)*
- **REQ-MC-049** — Registered modes.
